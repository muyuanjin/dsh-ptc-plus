# Archive Resolved Review Findings

## Problem

An ignored root `REVIEW_FINDINGS.md` prevents unresolved review findings from being committed only when every contributor remembers its informal format and checks it manually. Deleting a resolved ledger removes useful local evidence, while keeping it at the root makes later work indistinguishable from an active review. Tests and commit hooks also cannot enforce one lifecycle if each recognizes a different prose convention.

## Decision

`.agents/templates/REVIEW_FINDINGS.md` is the tracked schema owner for local review ledgers. Schema `dsh-review-findings/v3` separates each finding's stable required outcome, current implementation plan, accumulated resolution evidence, and optional accepted-disposition owner. A finding can be captured before diagnosis produces a plan; once a concrete correction is selected, the plan is recorded before implementation and kept synchronized when evidence changes the diagnosis, ownership, affected artifacts, or verification path. `resolutionEvidence` records completed facts rather than a chronological work transcript. A finding marked `resolved` retains its implemented plan. A finding marked `accepted` names a tracked document or HTTPS issue in `dispositionRef`; a local reference must be one exact tracked file that remains present in the source candidate, not a directory, pathspec match, or index entry deleted from the checkout. The local ledger cannot be the only copy of an intentionally retained limitation. The separate `.agents/templates/REVIEW_PLAN.json` owns the independent-review partition described by ADR 0026; a review plan routes verification work and invalidation, while the findings ledger owns discovered defects and their resolution.

Review output and ledger mutation follow task authority. A read-only review reports records in the ledger's semantic fields without writing checkout state. Every implementation preserves an active ledger, but an ordinary change with no finding does not create one. `npm run review:new` creates the ignored root ledger only when a task authorizes capture or resolution of at least one finding; implementation imports those findings before editing their fixes. Archives move under Git's local `review-findings/archive` metadata path, so they cannot enter a commit and remain associated with the checkout.

Ledger validation, readiness, deterministic verification, archive, and commit proof are distinct states with one implementation. `npm run review:validate` checks schema and tracked-file safety while accepting a valid open ledger. `npm run review:gate` is read-only: it blocks an open ledger, validates durable owners for accepted findings, and never archives. `npm run verify` performs schema validation before syntax and coverage checks, so open-ledger work can collect evidence. `npm run check` applies the readiness gate first, then materializes the current tracked and non-ignored checkout through Git's clean and index semantics in a temporary Git administrative directory. Git selects that directory's default index through `--git-dir` and reads the target checkout through `--work-tree`; it never receives an alternate-index environment path that could fall back to the real repository index. The temporary object database reads the repository's objects through a relative alternates entry and stores new fingerprint objects locally. The resulting tree object ID includes canonical blobs, symlink identity, and file modes while remaining independent of staged content. Sparse checkouts retain skip-worktree paths from the `HEAD` baseline and apply clean conversion only to materialized paths, so an absent out-of-cone file is neither lost nor mistaken for a deletion. Every path discovered by Git is reapplied through NUL-delimited literal input. The command separately snapshots the ignored ledger, runs `verify`, rejects changed source or ledger state, and refreshes the proof before archiving a resolved ledger. Repository scripts that launch npm as a child use one command resolver: an invoking npm process supplies its CLI path and Node executable, while direct script invocation falls back to the platform npm executable. A successful later check without an active ledger also refreshes an older proof. The pre-commit hook rejects open and unverified resolved ledgers, requires a verification proof for the current `HEAD`, requires equal source and index tree fingerprints, and requires the composite independent-review plan, lane verdicts, and final verdict defined by ADR 0026. Staging the complete verified tree permits repeated commit attempts; partial staging, additional staged content, mode-only changes, later checkout changes, uncovered paths, or invalidated lane dependencies require reconciliation before commit.

Hook installation is explicit. `npm run hooks:install` selects the tracked hook path only when the effective `core.hooksPath` is unset or already `.githooks`. Before the first switch from Git's default hooks directory, installation rejects any non-sample hook file there; it also rejects an incompatible configured path instead of disabling another hook owner. Dependency installation has no Git-configuration side effect.

## Alternatives considered

**Keep deleting resolved ledgers.** This preserves a clean root but discards useful local review history and leaves unresolved-commit prevention dependent on agent memory.

**Archive under an ignored worktree directory.** This is visible, but it requires another ignore rule and can still be force-added. Git's local metadata directory makes the non-commit property structural.

**Let the hook parse headings and status bullets independently.** This avoids YAML frontmatter but duplicates an informal Markdown parser across automation. A structured frontmatter schema keeps the human-readable file while giving tests and hooks one parser and one versioned shape.

**Use `requiredOutcome` as both acceptance condition and implementation plan.** This keeps one fewer field, but a changed implementation strategy would rewrite the definition of success and erase the distinction between what must hold and how the current work intends to make it hold. Separate fields keep the acceptance target stable while allowing the plan to evolve with evidence.

**Store a chronological implementation diary.** A detailed log preserves every intermediate action but turns a commit guard into a reasoning transcript and becomes expensive to keep accurate. The ledger retains the current plan and factual evidence; durable architectural rationale remains in the owning ADR.

**Install the hook whenever `core.hooksPath` is unset.** An unset configuration may still have active hooks under Git's default hooks directory. Switching paths would leave those files intact but stop invoking them, so installation checks both configured and default ownership and requires maintainers to compose competing hook sets explicitly.

**Block deterministic verification while a finding is open.** This prevents an unresolved change from appearing ready, but it also prevents the prescribed evidence from being collected before resolution. It loses because validation can accept a well-formed work-in-progress ledger while the later readiness and commit gates still reject it.

**Trust terminal ledger text as verification proof.** This keeps the gate simple, but a manually edited status cannot prove that deterministic verification ran or that it covered the same tree being committed. It loses because paired source and index fingerprints bind archive and commit readiness to both the observed verification run and the prospective commit.

**Keep accepted limitations only in the local archive.** This preserves review history without tracked documentation, but the decision disappears across clones while the limitation survives. It loses because acceptance is a durable product or engineering decision and therefore needs a durable owner.

**Install hooks from the package lifecycle.** This configures contributors automatically, but dependency installation then mutates Git governance or fails because of an unrelated hook owner. It loses because explicit setup preserves authority and keeps verification preparation free of configuration side effects.

**Choose `npm` or `npm.cmd` only from `process.platform`.** This works when the child process inherits a platform-native PATH, but fails when a Windows Node executable is reached through a WSL command shim and `npm.cmd` is not visible to Windows process lookup. Reusing npm's own CLI identity preserves the actual toolchain selection; the platform name remains only the fallback for direct script invocation.

## Consequences

Review findings have an explicit `reported -> authorized capture -> planned -> implemented and verified -> proof and archive -> matching commit -> proof retirement` lifecycle while retaining `open` and `resolved` as file-level states. An open ledger uses `verify` for deterministic evidence collection and fails `check` before its full gate runs; it also blocks commits. A resolved ledger remains active until verification succeeds against an unchanged source fingerprint, and commit readiness additionally requires the prospective index to match that fingerprint. Independent review lanes have their own `plan -> parallel review -> dependency-scoped retry -> deterministic proof -> composite verdict` lifecycle and do not replace finding disposition. Both local records stay outside source history; accepted limitations and durable architecture remain in tracked owners. Hook installation is an explicit checkout setup decision rather than a dependency-install side effect.
