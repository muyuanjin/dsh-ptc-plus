# Keep Global User Bindings Source-Owned and User-Controlled

## Problem

Repeated project helpers are useful across sessions, but ordinary REPL bindings belong to one session and cannot be promoted losslessly from a runtime value back into TypeScript module source. A persistent helper feature must keep executable values, model-visible declarations, storage, and cold recovery aligned without turning helpers into DSH tools or granting the model a second authority path for persistent changes and candidate execution.

## Decision

Global User Bindings is an optional PTC Plus capability controlled by `userBindingsEnabled`, which defaults to `false`. Disabled mode does not read storage, inject values or new declarations, register management RPC or commands, or render management UI. The next permitted accepted step can withdraw a previously delivered declaration through the PTC state snapshot contract in [ADR 0010](0010-session-log-derived-recovery-tips.md). Enabling the capability does not change DSH authority, approval, scheduling, cancellation, sandbox, or the code-only direct-tool projection.

Each entry is a TypeScript module with named value exports, a stable ID, display/call name, `namespace` or `top-level` scope, selected symbols, purpose, enabled state, and optional `modelContext`. Omitted symbol selection derives every named value export; an explicit selection limits the exposed API. One strict normalizer derives body-free declarations, binding kinds and durability from source, fingerprints the complete stored entry, and rejects any supplied derivative that disagrees. Activated entries are ordinary writable REPL bindings; a model redeclaration follows the configured binding policy and shadows the default only for that session.

`modelContext` contains `includeDeclaration` (default `true`) and `instructions` (default empty, at most 4096 UTF-16 code units). The checkbox controls injection of the existing source-derived interface; a nonempty prompt is injected independently. There is no separately authored interface. Unchecking the declaration and clearing the prompt omits both without disabling execution. Source-derived declarations remain canonical for conflict checks and recovery. The enabled set's selected declarations and prompts have an aggregate 16384-code-unit budget in addition to the existing source-derived declaration budget. The shared Client-safe metadata normalizer preserves these fields in accepted draft history.

Omitting `modelContext` preserves the existing entry serialization and fingerprint, so historical version 1 snapshots remain verifiable without rewriting journals. When present, normalized metadata participates in the existing fingerprint. Previously saved `enabled` and `declaration` fields retain their normalized representation for fingerprint verification, including the old declaration string limit of 8192 code units, but custom declarations no longer enter model or UI presentation. A legacy disabled prompt maps to `includeDeclaration: false` and empty instructions; otherwise its prompt is retained and the source-derived interface is included. An explicit `includeDeclaration` takes precedence. Editing and saving through the workbench writes current fields. Existing entries without metadata gain first-turn discovery through the default declaration setting.

For new cells, the complete snapshot fingerprint is an integrity check, not a module reuse key. For the same active entry ID, the worker reuses the module when its exact source, scope, namespace call name, and ordered selected exports match. Changes to model context, purpose, or a top-level entry's display name preserve module state and do not repeat initialization. Execution-input changes, removal, and disablement retain their activation and shadow rules. Each cell still records the complete current snapshot and fingerprint.

Journal version 6 requires `userBindingsReusePolicy`: new cells write `implementation-v1`, while closed versions 1 through 5 normalize to `fingerprint-v1`. The historical policy reuses a module only when the complete entry fingerprint matches, preserving the resets caused by purpose and top-level display-name changes. Version 5 retains its snapshot fingerprint; versions 1 through 4 retain their explicit no-snapshot migration. Replay passes each cell's recorded policy to the worker, including in mixed histories; subsequent live cells use the current policy without resetting a matching implementation merely because the policy changed. Normalizing a journal again preserves that policy. Missing or unknown policies invalidate historical evidence and contract the recoverable frontier without blocking the current valid cell. Replayed initializer calls return recorded values without redispatching host effects. Void completions do not prove internal state equivalence, so they cannot substitute for the recorded policy.

Namespace call names and selected export names must parse as exactly one Identifier whose AST name equals the complete supplied string. Whitespace, comments, binding patterns, extra declarations and escaped spellings cannot change identifier identity between validation, declarations, conflict checks, activation and recovery. Supported Unicode identifiers keep their exact spelling. Top-level entry display names remain separate from callable export names.

## Storage and Source Ownership

The Host owns one document at `$DSH_HOME/ptc-plus/bindings.json`. The store serializes mutations, holds a file lock, compares the last-read disk bytes, requires an expected revision, and atomically replaces the file with owner-only permissions. The complete enabled declaration budget is validated before replacement; an externally written document that exceeds the same budget is treated as damaged storage. A malformed document remains an explicit error, and stale or external changes require reload instead of blind overwrite. A new Agent draft uses create-only persistence so a concurrent entry with the same ID cannot be replaced.

The workbench keeps a save revision with the loaded source. Catalog-only changes cannot advance it unless a successful compare-and-swap operation proves the source unchanged. Reload synchronizes a read-only selection's source, declaration and baseline; a removed entry clears the selection. While editing, explicit reload preserves the draft and updates its save revision and cancel baseline. Catalog and entry reads must agree on revision before applying the reload. Stale responses cannot change a newer workbench. Reload neither saves nor executes code; changing the selected source releases its temporary console environment, while unchanged source retains that environment.

Source is the only implementation authority. Both candidate execution and session activation resolve relative imports from the directory containing `bindings.json`; a session cwd therefore cannot change a persistent helper's dependency graph. The parser accepts named value exports and rejects default exports, re-exports, reserved bindings, invalid selected symbols, and conflicting enabled call names. Model-visible declarations retain useful annotations and bounded inferred shapes but omit implementation bodies and private helpers.

## Runtime, Prompt, and Recovery

Prompt assembly captures the current enabled snapshot as the desired input later passed through dispatch. Its `tools:ptc-plus-user-binding-defaults` system section describes configured bindings from the first model turn, using each entry's nonempty prompt and its source-derived declaration when selected. Entries with neither are omitted. It never evaluates a module or claims successful activation. It explicitly states that modules initialize before cell execution, may fail, and may be shadowed by session-local bindings. Entries are ordered by stable ID; revision counters and activation facts do not enter this section. Under unchanged configured API text, model route and native capability view, the system prefix remains byte-stable. Saving and enabling a `/binding` draft, enabling an entry mid-session, and changing prompt settings all apply at the next assembly without waiting for activation or a new session. Merely accepting a disabled draft does not publish it.

The configured section enters DSH's renderer through the `ptc_plus_user_binding_defaults` assembly variable. DSH expands its value once, so prompts and source-derived declarations containing literal `{{...}}` syntax neither substitute host variables nor fail template validation.

The `tools:ptc-plus-user-bindings` section of the independently sourced PTC state snapshot remains narrower: it intersects that desired set with the current session worker's successfully activated snapshot and requires every call identifier in a complete entry to retain matching `user-global` provenance. A new or changed entry crosses one activation cell before it can receive an active declaration; presentation-only updates reuse the already initialized module during that cell. Both declaration surfaces obey `modelContext.includeDeclaration`; the independent prompt remains in the configured section. Binding contents do not modify `tools:sdk`, direct-tool schemas, or tool order. Ordinary requests receive neither module source nor management operations. Removing activation eligibility updates the PTC snapshot, explicitly withdrawing the old active claim without resending unrelated contexts or superseding authoring tasks and Skill instructions. Configured API documentation remains a statement of defaults and does not preserve session-local state across compaction or recovery.

The worker activates entries before the cell and reports entry-level failures without blocking independent code. A request-owned program namespace or error class takes precedence over a same-name user entry, which is excluded from that request's activated snapshot. Every current request namespace is also exposed to binding modules through a stable worker-global bridge, but each call resolves the AsyncLocalStorage execution lease that reached it; a continuation from a completed cell cannot borrow a later cell's capabilities. A request namespace that collides with any existing worker global fails before bridge installation because replacing a Node intrinsic cannot preserve both environments. BindingCatalog records `user-global` provenance and handles each entry atomically: if any of its call identifiers has a session-local shadow, the complete entry is omitted from activation and model projection. Namespace members and top-level exports read their live module values until assignment or a permitted redeclaration creates that shadow. Each settled cell persists the exact successfully activated snapshot in private result metadata, while journal versions 5 and 6 record its fingerprint or an explicit `null` when no snapshot exists. If a failed initializer issued a program call, the cell becomes volatile because that snapshot cannot supply its replay source. Cold recovery validates the journal-to-snapshot relation and executes recorded source rather than consulting the current store; missing, malformed, or source-inconsistent evidence contracts the recoverable frontier under the existing fail-closed journal rules.

An exported function may escape into an ordinary session binding before its global entry is updated, disabled, or removed. Reachability cannot be proved inside the worker, so every successfully exposed binding module retains its relative-import parent mapping and dynamic program-namespace bridge until that worker ends. Failed modules that expose no value release their temporary mapping. When no user binding has ever been exposed, disabled or empty activation installs no bridge; if every attempted activation fails, any bridge installed for that attempt is removed before the cell executes.

The workbench code console runs the current unsaved source draft in a separate bounded Node REPL worker and never accesses the Agent session kernel or its journal. Named exports are available directly; commands accept TypeScript and top-level await, return inspected expression values and logs, and preserve declarations across executions. Ordinary syntax and runtime errors preserve the environment and prior partial effects. The existing one-shot candidate RPC remains compatible. Both paths retain DSH process authority and can produce irreversible Node/OS effects before failure or cancellation; worker state isolation is not a security sandbox.

An authenticated user request lazily creates an opaque Host-generated environment handle. Each workbench owns its handle, one command at a time, with at most four environments per owner. Worker wall, output and memory limits use the existing configuration. Source and command inputs are each limited to 1 MiB. Ten minutes without code execution releases the worker without erasing displayed history. Source replacement at the next execution, switching entries, saving changed source, leaving the workbench, explicit reset, cancellation, timeout, output failure, worker failure, disablement or owner disposal also releases it. No action replays earlier commands automatically. Folding, ordinary editing and clearing displayed history do not execute code. The user may explicitly start again from the current draft after release.

## Agent-Assisted Authoring

An enabled agent whose effective public tool view contains `run_code` receives `/binding new <requirement>` and `/binding edit <id> <requirement>` through DSH's public command service. Eligibility is available before prompt assembly, follows `tools/change`, and does not infer capability from a preset label. The command registration belongs to an injected child fiber of the exact agent scope. A pending fiber installs when the command service becomes available; a callback whose eligibility expired fails and removes its placeholder. Lifecycle listener installation has its own generation, independent of request and projection changes. The Client uses DSH's session command directory and a compact `conversation.input.left` action, including before the first model turn.

Either command appends complete authoring instructions through `agent.steer` and completes admission once the normal Agent turn has been requested. Admission means authoring started, not that a candidate exists. Under enabled configuration, `code.submitBindingDraft({requestId, entry})` is a stable program SDK member, including its discovery schema. It uses the ordinary cell lease and program-call transcript. The Host captures the exact active request at cell creation and checks agent identity, request ID, generation, and single-submission eligibility before and after asynchronous validation. Acceptance, turn stop, error, cancellation, replacement, disablement, or disposal revokes submission eligibility without changing the declaration. No request-specific tool or Skill registration changes the system prefix. Cold replay returns a recorded receipt without submitting again or restoring writable access.

The schema, SDK and authoring instructions include both `modelContext` fields. Authoring asks for a prompt addressed to future models and a declaration-injection choice, with useful types maintained in source. Edits preserve existing prompt preferences unless the requirement changes them. The workbench exposes both controls directly, without requiring source-edit mode; changes enter an unsaved draft with save and cancel actions. The command card exposes accepted prompt metadata before a user saves it. Saving as disabled does not add configured API text to ordinary requests.

The first validated candidate becomes one disabled memory draft. Private `dshPtcPlusBindingDraft` metadata version 2 contains the generation, opaque locator, and the accepted candidate with request ID, command ID, version, mode, and complete source-owned entry. Later results carry `candidate: null`; version 1 remains readable. The `ptcPlusBindingDraft` projection, state version 4, pairs command and turn lifecycle with acceptance, retains read-only history across seeds and owner generations, and never revives a historical locator. Malformed historical presentation cannot block subsequent valid execution. Connection RPC uses `trusted-host` authority but provides no caller/session identity, so draft operations require the locator rather than a payload session ID. The `draft-review` endpoint serves the accepted source and any completed action while its owning lifecycle remains available.

After a user save or discard completes, the Host consumes the writable locator and appends a structured plugin notice through public `Session.append('user/message', ..., {surfaceOp: 'append', sourceEventSeqs: [acceptingResultSeq]})`. The notice contains only request ID, entry ID, saved/discarded state, and enabled state. It asserts persistence, never session activation, and contains no source or locator. The projection accepts it only when identity and the accepting source relation match. Card remounts use this historical source and action, never a later store entry with the same ID. A failed notice append cannot undo the write or restore save eligibility; missing durable evidence remains unknown after restart. In-flight storage settlement cannot resurrect a locator already revoked by lifecycle cleanup. Clearing an unsaved draft alone does not append a persistence notice.

Catalog revision conflicts refresh the catalog, draft, and review independently. A still-valid draft stays inspectable and retryable by the user; an authoritative empty draft revokes the actions. No conflict automatically repeats a write. Agent disposal invalidates only that exact Agent's locators and in-memory reviews; session disposal, feature disablement, and owner disposal revoke all affected access. Durable history proves a past action, not current activation or model knowledge.

The Agent can author a candidate but cannot persist, run, enable, remove, import, or inspect unrelated entries. Client actions remain separate: the conversation command card preserves the request, inspects source, and offers explicit save-as-disabled, save-and-enable, or discard actions for an accepted draft, while the shared REPL/Settings-modal workbench owns complete editing, validation, candidate execution, activation, import, and removal ([ADR 0024](0024-repl-console-observation.md)). Both save paths atomically claim the draft before checking the current catalog revision; save-and-enable writes the validated entry enabled in that same mutation. A concurrent discard receives a busy conflict instead of reporting success for a draft that can still reach storage.

## Alternatives considered

**Register each helper as a DSH tool.** Rejected because it changes dispatch and approval semantics and duplicates DSH's capability ownership instead of extending the REPL value environment.

**Register and unregister a handoff tool per request.** Rejected because transient transaction eligibility changes the complete SDK prefix on both entry and exit. A stable internal API with Host transaction prerequisites preserves the same authority and one-submission contract without those changes.

**Expose persistent management operations to the model.** Rejected because an ordinary model error could change every future session. A request-scoped draft handoff preserves assisted authoring while leaving durable and effectful actions under explicit user control.

**Promote a session binding into global storage.** Rejected because runtime values and bounded declaration provenance do not reconstruct complete module source, imports, comments, and types. Persisting a guessed representation would claim losslessness that the system cannot prove.

**Store source and metadata in separate files.** Rejected because source, symbol selection, purpose, and activation state would gain independent write and recovery histories. One atomically replaced document keeps identity and implementation under one owner while `.ts` import supports file-based authoring.

**Resolve helper imports from each session cwd.** Rejected because the same persistent entry could load different dependencies in candidate validation, live activation, and replay. The storage directory is stable across those paths.

## Consequences

Users can maintain typed helpers once and reuse them across sessions while models receive compact callable declarations and ordinary REPL values. Storage, prompt projection, execution, and replay share one source-derived identity, so recovery fails closed instead of substituting current external state. Session-local experimentation remains cheap and cannot silently overwrite the global default.

The cost is an opt-in management surface, a bounded declaration/context addition when entries are active, source evaluation at activation and replay, revision conflicts that require explicit reload, and user console execution whose external effects cannot be undone. The REPL view and Settings modal share full editing, code execution, import and removal; the conversation command card adds explicit draft save choices and does not expose Agent authority or unrelated entry management.
