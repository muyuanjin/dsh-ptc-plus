# Keep Global User Bindings Source-Owned and User-Controlled

## Problem

Repeated project helpers are useful across sessions, but ordinary REPL bindings belong to one session and cannot be promoted losslessly from a runtime value back into TypeScript module source. A persistent helper feature must keep executable values, model-visible declarations, storage, and cold recovery aligned without turning helpers into DSH tools or granting the model a second authority path for persistent changes and candidate execution.

## Decision

Global User Bindings is an optional PTC Plus capability controlled by `userBindingsEnabled`, which defaults to `false`. Disabled mode does not read storage, inject values or new declarations, register management RPC or commands, or render management UI. The next permitted accepted step can withdraw a previously delivered declaration through the PTC binding catalog contract in [ADR 0010](0010-session-log-derived-recovery-tips.md). Enabling the capability does not change DSH authority, approval, scheduling, cancellation, sandbox, or the code-only direct-tool projection.

Each entry is a TypeScript module with named value exports, a stable ID, display/call name, `namespace` or `top-level` scope, selected symbols, purpose, enabled state, and optional `modelContext`. Omitted symbol selection derives every named value export; an explicit selection limits the exposed API. One strict normalizer derives body-free declarations, binding kinds and durability from source, fingerprints the complete stored entry, and rejects any supplied derivative that disagrees. Activated entries are ordinary writable REPL bindings; a model redeclaration follows the configured binding policy and shadows the default only for that session.

New-generation export descriptors consume the shared TypeScript value normalizer used by module compilation, including enum and namespace values and erased type-only declarations. Original type-name evidence remains available for bounded signature projection. Validation derives this evidence without executing module source; historical snapshot transforms retain their recorded descriptor rules.

`modelContext` contains `includeDeclaration` (default `true`) and `instructions` (default empty, at most 4096 UTF-16 code units). The checkbox controls injection of the existing source-derived interface; a nonempty prompt is injected independently. There is no separately authored interface. Unchecking the declaration and clearing the prompt omits both without disabling execution. Source-derived declarations remain canonical for conflict checks and recovery. The enabled set's selected declarations and prompts have an aggregate 16384-code-unit budget in addition to the existing source-derived declaration budget. The shared Client-safe metadata normalizer preserves these fields in accepted draft history.

Omitting `modelContext` preserves the existing entry serialization and fingerprint; stored documents need no migration. Historical snapshot recovery additionally requires the transform evidence described below. When present, normalized metadata participates in the existing fingerprint. Previously saved `enabled` and `declaration` fields retain their normalized representation for fingerprint verification, including the old declaration string limit of 8192 code units, but custom declarations no longer enter model or UI presentation. A legacy disabled prompt maps to `includeDeclaration: false` and empty instructions; otherwise its prompt is retained and the source-derived interface is included. An explicit `includeDeclaration` takes precedence. Editing and saving through the workbench writes current fields. Existing entries without metadata gain first-turn discovery through the default declaration setting.

For new cells, the complete snapshot fingerprint is an integrity check, not a module reuse key. For the same active entry ID, the worker reuses the module when its exact source, scope, namespace call name, and ordered selected exports match. Changes to model context, purpose, or a top-level entry's display name preserve module state and do not repeat initialization. Execution-input changes, removal, and disablement retain their activation and shadow rules. Each cell still records the complete current snapshot and fingerprint.

Journal version 6 introduced the required `userBindingsReusePolicy`: new cells write `implementation-v1`, while closed versions 1 through 5 normalize to `fingerprint-v1`. Later closed generations keep the field required: version 6 retains its recorded policy, and version 7 adds the import-expression boundary documented in [ADR 0014](0014-persist-cell-rewrite-policy.md). Version 8 adds the required `userBindingsShadowPolicy` and the per-name evidence a settled new cell records under it, without changing the reuse policy's meaning; the two generations stay independent, so a cell can replay per-name attachment under either reuse policy. The historical policy reuses a module only when the complete entry fingerprint matches, preserving the resets caused by purpose and top-level display-name changes. Version 5 and later retain their snapshot fingerprint; versions 1 through 4 retain their explicit no-snapshot migration. Replay passes each cell's recorded policy to the worker, including in mixed histories; subsequent live cells use the current policy without resetting a matching implementation merely because the policy changed. Normalizing a journal again preserves that policy. Missing or unknown policies invalidate historical evidence and contract the recoverable frontier without blocking the current valid cell. Replayed initializer calls return recorded values without redispatching host effects. Void completions do not prove internal state equivalence, so they cannot substitute for the recorded policy.

Namespace call names and selected export names must parse as exactly one Identifier whose AST name equals the complete supplied string. Whitespace, comments, binding patterns, extra declarations and escaped spellings cannot change identifier identity between validation, declarations, conflict checks, activation and recovery. Supported Unicode identifiers keep their exact spelling. Top-level entry display names remain separate from callable export names.

## Storage and Source Ownership

The Host owns one document at `$DSH_HOME/ptc-plus/bindings.json`. The store serializes mutations, holds a file lock, compares the last-read disk bytes, requires an expected revision, and atomically replaces the file with owner-only permissions. The complete enabled declaration budget is validated before replacement; an externally written document that exceeds the same budget is treated as damaged storage. A malformed document remains an explicit error, and stale or external changes require reload instead of blind overwrite. A new Agent draft uses create-only persistence so a concurrent entry with the same ID cannot be replaced.

The workbench keeps a save revision with the loaded source. Catalog-only changes cannot advance it unless a successful compare-and-swap operation proves the source unchanged. Reload synchronizes a read-only selection's source, declaration and baseline; a removed entry clears the selection. While editing, explicit reload preserves the draft and updates its save revision and cancel baseline. Catalog and entry reads must agree on revision before applying the reload. Stale responses cannot change a newer workbench. Reload neither saves nor executes code; changing the selected source releases its temporary console environment, while unchanged source retains that environment.

Source is the only implementation authority. Both candidate execution and session activation resolve relative imports from the directory containing `bindings.json`; a session cwd therefore cannot change a persistent helper's dependency graph. The parser accepts named value exports and rejects default exports, re-exports, reserved bindings, invalid selected symbols, and conflicting enabled call names. Model-visible declarations retain useful annotations and bounded inferred shapes but omit implementation bodies and private helpers.

`internal/stateful-module-compiler.js` owns binding-module compilation, shared by validation, live/cold activation, candidate execution and the draft console. Its maintained TypeScript transform owner remains `internal/typescript-transform.js`. Snapshot version 2 records either the historical `amaro@1.1.11` transform or `stateful-module-v1+amaro@1.1.11`, and includes that exact identity in the snapshot fingerprint. The latter applies the shared logical scope rules before TypeScript transformation; the former retains its historical lowering. Entry fingerprints and stored source remain source-owned. Unsupported identities cannot be substituted with the current compiler, and a transform change participates in runtime reuse identity. The complete language and journal-generation decision is [ADR 0025](0025-use-versioned-logical-binding-identities.md).

Version 1 snapshots did not record the native compiler. A matching source,
declaration, durability classification or cell completion does not prove matching
module values: an enum initializer can change a saved value while its cell returns
`undefined`. Nonempty version 1 snapshots therefore cannot prove a recovery
frontier. Existing journal recovery contracts at that cell and its dependent
suffix, persists and reports the contraction once, and executes the current
valid cell. It does not replay discarded effects, rewrite the historical log or
modify stored binding entries. Empty version 1 snapshots retain their original
fingerprint and remain usable as recovery evidence; subset selection preserves
the snapshot version and transform identity. Reconstructable cells still obey
their recorded module-reuse policy independently of the transform identity.
Ordinary REPL cells use the shared scope normalization and source-position contract with their recorded cell language generation.

## Runtime, Prompt, and Recovery

Prompt assembly captures the current enabled snapshot as the desired input later passed through dispatch. Its `tools:ptc-plus-user-binding-defaults` context describes configured bindings from the first model turn, using each entry's nonempty prompt and its source-derived declaration when selected. Entries with neither are omitted. It never evaluates a module or claims successful activation. The catalog wrapper identifies use inside `run_code` and replacement of the previous global binding API reference. Entry labels, selected prompts and declarations form the entire body; initialization failures belong to execution results. Entries are ordered by stable ID; revision counters and activation facts do not enter this context. It belongs to the independently sourced PTC binding API catalog, appended at the matching accepted `agent/pre-step` under the Host's runtime-context permissions. Saving and enabling a `/binding` draft, enabling or removing an entry mid-session, and changing prompt settings update the next permitted request without waiting for activation or a new session. Merely accepting a disabled draft does not publish it.

Configured prompts and interfaces never enter `PromptAssembly.sections` or its variables. Entry changes preserve the complete system text and ordered tool schemas; they append a new binding catalog that supersedes the earlier catalog, including an explicit empty catalog when no configured documentation remains. Committed messages and the public ordered surface own deduplication, restart reconstruction and reassertion after compaction. Rejected, cancelled or runtime-suppressed steps do not mark delivery; the next permitted request reconciles current configuration. Host runtime-context clearances do not withdraw a retained catalog, and recovery snapshot updates do not resend it. Text is delivered literally, so `{{...}}` in prompts or source-derived declarations neither substitutes Host variables nor invokes template validation. No per-session frozen configuration cache or second persistence store is introduced.

Configured documentation is the only new model-visible source of binding prompts and interfaces. Successful activation, session-local shadows and worker reconstruction do not append an activation announcement or resend an unchanged configuration. Execution results and diagnostics own actual execution facts; an availability check observes a known name without external effects. A separate active-declaration channel would duplicate the configured API and make every first successful cell repeat the whole binding context. The reader still accepts historical binding configuration and `tools:ptc-plus-user-bindings` sections: the next permitted accepted recovery snapshot omits them and explicitly supersedes the earlier claims once, including when bindings are disabled. Current documentation is supplied independently as a catalog. Existing messages and journals are not rewritten. Binding contents do not modify `tools:sdk`, direct-tool schemas, or tool order. Ordinary requests receive neither module source nor management operations. Configured API documentation remains a statement of defaults and does not preserve session-local state across compaction or recovery.

The worker activates entries before the cell and reports entry-level failures without blocking independent code. A request-owned program namespace or error class takes precedence over a same-name user entry, which is excluded from that request's activated snapshot. Every current request namespace is also exposed to binding modules through a stable worker-global bridge, but each call resolves the AsyncLocalStorage execution lease that reached it; a continuation from a completed cell cannot borrow a later cell's capabilities. A request namespace that collides with any existing worker global fails before bridge installation because replacing a Node intrinsic cannot preserve both environments. BindingCatalog records `user-global` provenance and attaches current entries per call identifier: a session-local shadow suppresses only that name from subsequent global activation while the entry's remaining names keep activating, so one local override neither erases a sibling helper nor resets the module state that provides it. Journals migrated from versions 1 through 7 keep the historical whole-entry suppression, and `userBindingsShadowPolicy` fixes which rule each cell replays under. Namespace members and top-level exports read their live module values until assignment or a permitted redeclaration creates that shadow. Each settled cell persists the exact successfully activated snapshot in private result metadata, while journal versions 5 and later record its fingerprint or an explicit `null` when no snapshot exists. Per-name cells additionally record the `provider`/`local`/`absent`/`unknown` attachment facts the worker reported at settlement, validated against that snapshot. Replay re-activates the recorded snapshot and re-executes the recorded source, then requires the facts reported during that replay to equal the recorded ones: the record verifies replay instead of installing names, and a divergence is rejected rather than resolved from the current store. If a failed initializer issued a program call, the cell becomes volatile because that snapshot cannot supply its replay source. Cold recovery validates the journal-to-snapshot relation and executes recorded source rather than consulting the current store; missing, malformed, or source-inconsistent evidence contracts the recoverable frontier under the existing fail-closed journal rules.

An exported function may escape into an ordinary session binding before its global entry is updated, disabled, or removed. Reachability cannot be proved inside the worker, so every successfully exposed binding module retains its relative-import parent mapping and dynamic program-namespace bridge until that worker ends. Failed modules that expose no value release their temporary mapping. When no user binding has ever been exposed, disabled or empty activation installs no bridge; if every attempted activation fails, any bridge installed for that attempt is removed before the cell executes.

Installed provider setters can likewise remain callable after their entries disappear. BindingCatalog retains their name eligibility along the accepted execution ancestry, separately from current entries and the visible binding inventory. A later setter write may therefore establish a local value without reactivating its provider. Provider facts still require the current activated snapshot and must not conflict with request-owned names; failed activation or preflight does not establish historical eligibility. Worker reset clears this evidence, and cold replay rebuilds it only from the retained verified ancestry, including historical whole-entry cells. Recovery contraction cannot carry eligibility across a discarded boundary.

The workbench code console runs the current unsaved source draft in a separate bounded Node REPL worker and never accesses the Agent session kernel or its journal. Named exports are available directly; commands accept TypeScript and top-level await, return inspected expression values and logs, and preserve declarations across executions. Ordinary syntax and runtime errors preserve the environment and prior partial effects. The existing one-shot candidate RPC remains compatible. Both paths retain DSH process authority and can produce irreversible Node/OS effects before failure or cancellation; worker state isolation is not a security sandbox.

An authenticated user request lazily creates an opaque Host-generated environment handle. Each workbench owns its handle, one command at a time, with at most four environments per owner. Worker wall, output and memory limits use the existing configuration. Source and command inputs are each limited to 1 MiB. Ten minutes without code execution releases the worker without erasing displayed history. Source replacement at the next execution, switching entries, saving changed source, leaving the workbench, explicit reset, cancellation, timeout, output failure, worker failure, disablement or owner disposal also releases it. No action replays earlier commands automatically. Folding, ordinary editing and clearing displayed history do not execute code. The user may explicitly start again from the current draft after release.

## Agent-Assisted Authoring

An enabled agent whose effective public tool view contains `run_code` receives `/binding new <requirement>` and `/binding edit <id> <requirement>` through DSH's public command service. Eligibility is available before prompt assembly, follows `tools/change`, and does not infer capability from a preset label. The command registration belongs to an injected child fiber of the exact agent scope. A pending fiber installs when the command service becomes available; a callback whose eligibility expired fails and removes its placeholder. Lifecycle listener installation has its own generation, independent of request and projection changes. The Client uses DSH's session command directory and a compact `conversation.input.left` action, including before the first model turn.

Either command appends complete authoring instructions through `agent.steer` and completes admission once the normal Agent turn has been requested. Admission means authoring started, not that a candidate exists. Under enabled configuration, `code.submitBindingDraft({requestId, entry})` is a stable program SDK member, including its discovery schema. It uses the ordinary cell lease and program-call transcript. The Host captures the exact active request at cell creation and checks agent identity, request ID, generation, and single-submission eligibility before and after asynchronous validation. Acceptance, turn stop, error, cancellation, replacement, disablement, or disposal revokes submission eligibility without changing the declaration. No request-specific tool or Skill registration changes the system prefix. Cold replay returns a recorded receipt without submitting again or restoring writable access.

The schema, SDK and authoring instructions include both `modelContext` fields. Authoring asks for a declaration-injection choice and a usage prompt containing only information missing from the interface; when types and API comments suffice, the prompt is empty. Edits preserve existing prompt preferences unless the requirement changes them. The workbench exposes both controls directly, without requiring source-edit mode; changes enter an unsaved draft with save and cancel actions. The input-dock review exposes accepted prompt metadata before a user saves it; the command card retains read-only history. Saving as disabled does not add configured API text to ordinary requests.

Authoring uses ordinary `run_code` cells to develop and test pure logic with in-memory inputs, assertions and substitutes. Temporary session variables are permitted; the task prohibits test effects on external files and services. Imports and initializers with unknown effects are reviewed without execution. Tests can guide corrections and comparisons before the final source, exports, types and usage prompt are checked together. The answer reports verified behavior and untested integration, without requiring reasoning transcripts or a fixed number of calls. This is task guidance under DSH authority, not a sandbox or an additional permission mechanism. It does not expose the workbench's candidate runner to the Agent.

The existing REPL supplies execution feedback; the handoff accepts final source for user review. Each tool's instructions describe its own task and required inputs. Deterministic Host scenarios verify the execution and submission contracts; explicitly configured model runs evaluate actual authoring behavior. See [binding workflow evaluation](../evaluation.md#binding-workflow).

The first validated candidate becomes one disabled memory draft. Private `dshPtcPlusBindingDraft` metadata version 2 contains the generation, opaque locator, and the accepted candidate with request ID, command ID, version, mode, and complete source-owned entry. Later results carry `candidate: null`; version 1 remains readable. The `ptcPlusBindingDraft` projection, state version 4, pairs command and turn lifecycle with acceptance, retains read-only history across seeds and owner generations, and never revives a historical locator. Malformed historical presentation cannot block subsequent valid execution. The management Remote uses the authenticated Host Gateway and provides no caller/session identity, so draft operations require the locator rather than a payload session ID. The `draft-review` endpoint serves the accepted source and any completed action while its owning lifecycle remains available.

After a user save or discard completes, the Host consumes the writable locator and appends a structured plugin notice through public `Session.append('user/message', ..., {surfaceOp: 'append', sourceEventSeqs: [acceptingResultSeq]})`. The notice contains only request ID, entry ID, saved/discarded state, and enabled state. It asserts persistence, never session activation, and contains no source or locator. The projection accepts it only when identity and the accepting source relation match. Card remounts use this historical source and action, never a later store entry with the same ID. A failed notice append cannot undo the write or restore save eligibility; missing durable evidence remains unknown after restart. In-flight storage settlement cannot resurrect a locator already revoked by lifecycle cleanup. Clearing an unsaved draft alone does not append a persistence notice.

Catalog revision conflicts refresh the catalog, draft, and review independently. A still-valid draft stays inspectable and retryable by the user; an authoritative empty draft revokes the actions. No conflict automatically repeats a write. Agent disposal invalidates only that exact Agent's locators and in-memory reviews; session disposal, feature disablement, and owner disposal revoke all affected access. Durable history proves a past action, not current activation or model knowledge.

The Agent's handoff API cannot persist, execute, enable, remove or import stored candidates, or inspect unrelated entries. Session-local tests use ordinary REPL execution as described above. Client actions remain separate: the conversation command card preserves the request and read-only accepted source; one current review controller in the published input dock offers explicit save-as-disabled, save-and-enable, or discard actions, while the shared REPL/Settings-modal workbench owns complete editing, validation, candidate execution, activation, import, and removal ([ADR 0024](0024-repl-console-observation.md)). Both save paths atomically claim the draft before checking the current catalog revision; save-and-enable writes the validated entry enabled in that same mutation. A concurrent discard receives a busy conflict instead of reporting success for a draft that can still reach storage.

## Alternatives considered

**Register each helper as a DSH tool.** Rejected because it changes dispatch and approval semantics and duplicates DSH's capability ownership instead of extending the REPL value environment.

**Register and unregister a handoff tool per request.** Rejected because transient transaction eligibility changes the complete SDK prefix on both entry and exit. A stable internal API with Host transaction prerequisites preserves the same authority and one-submission contract without those changes.

**Expose persistent management operations to the model.** Rejected because an ordinary model error could change every future session. A request-scoped draft handoff preserves assisted authoring while leaving durable and effectful actions under explicit user control.

**Promote a session binding into global storage.** Rejected because runtime values and bounded declaration provenance do not reconstruct complete module source, imports, comments, and types. Persisting a guessed representation would claim losslessness that the system cannot prove.

**Store source and metadata in separate files.** Rejected because source, symbol selection, purpose, and activation state would gain independent write and recovery histories. One atomically replaced document keeps identity and implementation under one owner while `.ts` import supports file-based authoring.

**Resolve helper imports from each session cwd.** Rejected because the same persistent entry could load different dependencies in candidate validation, live activation, and replay. The storage directory is stable across those paths.

## Consequences

Users can maintain typed helpers once and reuse them across sessions while models receive compact callable declarations and ordinary REPL values. Storage, prompt projection, execution, and replay share one source-derived identity, so recovery fails closed instead of substituting current external state. Session-local experimentation remains cheap and cannot silently overwrite the global default.

The cost is an opt-in management surface, a bounded configured declaration/context addition when entries are enabled, source evaluation at activation and replay, revision conflicts that require explicit reload, and user console execution whose external effects cannot be undone. The REPL view and Settings modal share full editing, code execution, import and removal; the input-dock review provides explicit draft save choices and does not expose Agent authority or unrelated entry management.
