# 能力面：概念契约

## 0. 这份文档约束什么

「能力面」是唯一一个陈述**某个地址上、某条能力给不给、给多少**的页面。它只有一个渲染器、一套词、一条写通道、一种回执。多入口合法，多页面非法。

本文决定形状。代码与本文不一致处，代码是缺陷；本文与下面这条红线不一致处，本文是缺陷：

> 一格的取值不得由「某个进程／服务／运行时／命令没有在运行，或某个全局开关没有启用」改变。判定：把那个来源摘掉，这个值会变吗？
>
> 两列都陈述各自记录的字：记录写 `automatic` 就上屏 `automatic`，记录写 `closed` 就上屏 `closed`；保存列没为这个对象写下就写 `自动`，本会话列没有记录写 `继承`——绑定行的记录是采纳记录，它写 `使用`／`不使用`／`记录损坏`，没写下时回执写 `未写下`，不借用 `继承`。解析（这些字在运行时意味着什么）属于行为，不属于页面，任何一步解析的结果都不上屏；由 server 层记录作答、而成员自己的条目没有写下那一维时，回执列点名那一层（§8.1b）。本会话列的样式（行左缘色条、启用格内的状态标记、词的颜色与字重）只让这些字更快被读出，不新增值、不改写入判定：一个状态既不被样式创造，也不因样式缺席而消失。保存列的样式同理只让保存列自己的字更快被读出：`开启`／`关闭` 用成功/错误色并加粗、`自动` 用业务色，所以没有本会话列的设置入口也读得出这份记录把哪些对象写成关闭。两列的样式都不表示这一行在这里得到什么：保存条目、类别规则与 `mcpServers.<server>` 规则在运行时谁压住谁属于解析（§8.1b、§8.1c），既不上屏，也不成为另一列的颜色。

非目标：不改冻结方案语义与 `/capabilities refresh` 的同步边界；不改写通道（一个写者、一种回执）；统计采集与预算预览不在本页（见 §5）。

## 1. 概念

| 概念 | 回答 | 边界（属于／不属于） | 后果 | 邻居 |
| --- | --- | --- | --- | --- |
| **页面** | 哪些决定必须共用一套词、一条写通道、一种回执 | 属于：对象集、维度集、每地址一列值、一条写通道、一次全成功或全失败的读。不属于：打开它的位置、容器、显示多少列 | 同一（对象, 地址）处处同值、同词、同记录、同回执；任一项不同即第二个页面 | 组件（机制）；入口（到达位置） |
| **入口** | 从哪来、这次带来哪些地址 | 属于：打开位置、地址集、跨越生效边界的动作。不属于：任何值、任何词、列义（行集不由入口挑选，而随它固定的地址集推出：绑定采纳没有保存地址，所以绑定行只出现在会话入口；设置入口读未点名会话的宿主声明，会话入口读该会话的声明面，两者是同一份读的两个作用域，入口不能只挑其中一部分行） | 只能缩小**决定集**，不能缩小地址集；地址集的变化只表现为整列存在／不存在 | 页面；地址 |
| **地址** | 这条决定写进哪份记录、从哪一刻被读到 | 属于：新会话默认／本会话两个值及其生效边界。不属于：值本身、观察对象、任何运行状态 | 两份记录互不改写；「已保存」不等于「已生效」 | 观察对象（读谁的事实） |
| **供给** | 这个地址上有哪些对象各自可以被单独决定 | 属于：该地址的声明面（宿主对该作用域声明的工具、Skill、MCP 服务、绑定条目）。不属于：配置、记录、证据、统计、装了什么 | 供给没有就没有行；能单独决定才成行 | 规则的适用面（规则谈论尚未供给的对象） |
| **给不给** | 这个地址上这个对象给不给 | 属于：给／不给，以及没有选择时由规则或宿主推导。不属于：给多少、能不能跑、装没装上、用没用过 | 不给时说明、发现、执行三面一致地不体现它；不删偏好、不删行 | 给多少；供给；证据 |
| **给多少** | 给的时候契约以什么方式、占多少上下文 | 属于：沿用宿主／完整／按需／按依据分配，及其依据与额度参数。不属于：可执行性、实测占用、统计样本 | 显式完整不被预算降级；超预算被陈述但不改决定 | 观察（预算预览与覆盖率） |
| **规则** | 一个还没有被逐个决定的对象，值从哪来 | 属于：默认地址上的默认／类别／来源／单项覆盖顺序与区域参数。不属于：行、本会话记录、观察 | **只有默认地址需要规则**，因为它要陈述尚未供给的对象；本会话地址只有记录 | 行决定（优先级见 §2 裁决三） |
| **观察** | 已经发生了什么／照现在会得到什么 | 属于：覆盖率、样本状态、预算占用、已投递方案与当前记录的差异。不属于：决定的值、控件、行集、任何「能不能改」的条件 | 永远只读；缺就是空表或一句样本状态，绝不让控件消失或变灰 | 决定；证据；地址 |
| **证据** | 这个会话里有没有被接受执行证明拿到过 | 属于：已结算结果里的 used。不属于：选择记录、统计覆盖、模型是否知道 | 有就是标记，没有就是没有那件事；不属于决定页（裁决四） | 观察（派生）；给不给（允许） |
| **回执** | 这条决定留下哪张回执 | 属于：写入者给出的记录地址与内容。不属于：决定的值、证明程度 | 一次写入一条回执；回执点名写进哪份记录、什么值 | 证据（内容 vs 地址） |

**写权与控件是两个词，按地址种类定义。** 地址有两种：**对象地址**写某一条能力自己的条目，**规则地址**写某个作用域的规则（例如 `mcpServers.<server>`）。写权只回答「这一格写哪条地址」——会话入口的格写本会话记录，设置入口的格写保存文档；入口一打开就固定，与当前可写性无关。控件存在只回答「这次入口是否固定了这一格所写的那条地址」：固定了就一定有控件，只读或插件停用只把它禁用、不撤掉，别的层为这一维作答也不撤掉。服务行陈述的是规则，它的保存格编辑的就是那份规则文档里的那一条，所以这条定义对服务行同样成立，不需要例外。

## 2. 四条裁决（均以反例定，不以偏好定）

**裁决一：第一维用「启用」，废「可用性」。**
反例：产品里没有「并发上限」，本会话也没采纳「写入前备份」。用「可用性」时「并发上限」那格只能写「不可用」——一个按不动的控件，而「不可用」不是值、不是决定、不在任何记录里；救法只有灰掉一格或一格写「可用·未启用」。
判据：**这一格的控件按下与不按下的区别，是否由本页写下的一句话造成？** 不是 → 不许作带控件列的值。

**裁决二：第二维用「披露」，废「说明方式」，且取值必须换成「谁读得到、从哪一刻」。**
反例：磁盘满、备份没建立，人要「别解释」但模型必须知道。用「说明方式」时这格要写「不说明」，而「不说明」不是一种说明方式：写「摘要」与人要求相反，留空与「缺失即没有那格」冲突，新增「无」则列名与取值自相矛盾。
判据：**列出该列名全部合法取值；若存在常见会话使这格在列名 A 下必须写 A 不承认的值，而列名 B 下写得出一个真实地址，取 B。**

**裁决三：保存与本会话是两个概念、两格。**
反例：项目记录「写入前备份=开」是三周前别人保存的；本次会话要跑一次性实验必须关，团队默认必须保持开。一格一值时「下次开会话会怎样」与「这一格现在是什么」答案相反。
判据：**存不存在一个合法会话，使两份记录的当前值相反、且两个值都要被读到？** 存在 → 两个概念两格。

**裁决四：证据列移出决定页，换成「回执」列。**
反例：还没测时每行证据格空着——有格无值；测了且与决定相反时同一行两个真值来源矛盾（启用=是，证据=未建立）；证据会馊，要加时间或重测，那格就同时写请求与结果。
判据：**删掉这一列，本页还有没有哪个决定因此不可判定？** 删证据，每个决定照样可判；删回执，「这条决定去哪对账」不可判。

## 3. 三条不变式（改写后）

1. **入口只能缩小这批决定，不能缩小这些决定要读的地址；一个决定只要还在页上，它需要的全部地址就必须同时在场。**
   反例：从「项目」入口只看到保存值「开」，而这一回合跑的是会话记录里的「关」——每个字都为真，屏幕在说假话。
2. **带控件的格子只写决定，并且它自己就确定自己的地址；一格的读法若需要同行另一格才能确定，必须拆成两格或把地址写进格子。**
   反例：「披露=仅模型」在保存=开时指「下一会话第一格读得到」，在会话=关时这话不成立。值没变、地址由邻格决定——一格一值两地址，比一格两值更难发现。
3. **缺失是该地址上的一份「未写下」回执；「没有那一格」只表示该坐标不在此页地址集，且此页必须能报出自己的地址集。**
   反例：没有这一版产品／本会话还没决定／决定被撤回，三种缺失在屏幕上一模一样；恢复会话时读到空，分不清「从未写下」与「写下又撤回」，而后者可能已按旧值跑过。

## 4. 页面形状与入口

七列：`对象 | 类型 | 来源 | 保存·启用 | 保存·披露 | 本会话·启用 | 本会话·披露`，外加 `回执` 列（会话入口）。

| 作用域 ＼ 入口 | 会话入口（固定本会话） | 设置入口（固定新会话默认） |
| --- | --- | --- |
| 保存 | **只陈述**（本次入口没有固定它） | 陈述 + 控件 |
| 本会话 | 陈述 + 控件；无记录写 `继承` | **整列不存在**（该记录在本页没有所有者） |

控件存在 ⟺ 该格陈述的地址被这次入口固定。写权在打开时确定，显示永不改变写权。

由此推出两条产品事实，不需要另加规则：在会话里看得到默认值但改不了它——要改默认就换入口；保存的改动到新会话的第一次读取才被读到，它不等于「已生效」。

每个取值都是它那一列问题的答案，列名对每个取值都成立：

- `保存·启用` / `保存·披露`：配置为**这个对象**写下的那一维的值（`启用` / `关闭`，或四种披露之一）。每一维独立判断：记录没为这个对象写下这一维时写 `自动`——那是「这一维在这份记录里没有值」，不是一个被推导出来的默认。分类规则、成员行上的 server 规则与文档底层都会在运行时为这个对象作答，但那是解析：它们不是这个（对象, 地址）持有的字，因此不上屏、不改值，也不撤掉控件（§8.1c）。
- `本会话·启用` / `本会话·披露`：会话入口的能力行两格是下拉，写的是本会话记录对这一维的决定；记录没写就写 `继承`。由 server 层记录决定的那一维，值列仍写 `继承`（这一对象自己的记录没有字），回执列点名那一层（`经 mcpServers.<server>`）——那一层的规则由它自己那一行写。能力行的两格是控件而不是陈述：因为值列写的是这一格自己的记录，写下去一定看得见；绑定行的两格由采纳记录的形状决定，见 §8.4。
- `保存·披露` / `本会话·披露`：`人机·原文·首轮` / `人机·全文·首轮` / `仅模型·目录·首轮` / `仅模型·分配·不重读`——前两半回答「谁读得到」（人机同读／仅模型），后半回答「从哪一刻」（首轮起／不重读）。记录没为这个对象写下时，保存列写 `自动`、本会话列写 `继承`；MCP 服务无自身披露，两格写 `各成员自定`。
- `回执`：这条决定留下哪张记录，以及那份记录在该行上**写下的字**：`本会话记录 · <dimension> <记录原文>`；由上一层记录决定时写 `本会话记录 · 经 <layer> · <dimension> <记录原文>`。该地址没写下时写 `未写下`。绑定行的记录是采纳记录，写 `绑定采纳记录 · 使用／不使用／记录损坏`，没写下时同样写 `未写下`。

## 5. 观察面不在本页

统计、预算预览、覆盖率只有被试（会话家族 × 工作区 × 时间窗），不落在任何行上。它们不属于本页；若留在设置里，必须自认被试，且不得借用本页的列、行与分区标题——取值词表共用是唯一例外，见 §8.6。ADR 0040 后果段「观察需要一个活跃 PTC 会话」与本契约冲突：本页观察不落在任何行上，而 ADR 仍把它写成后果。两者由 ADR 0040 拥有，本契约只能记录冲突与取舍需求（观察面留在设置里时必须自认被试，或由 ADR 修订把这条后果收窄），不能单方面宣布它失效。

## 6. 唯一渲染器

本页的渲染器是 `src/client-capabilities-view.js` 的会话能力面。**出现第二个渲染器即缺陷**：任何入口都必须挂它，不得自带列、词、控件或回执。

- 设置页工作台的能力详情栏、`tools.edit` 弹窗随本契约删除。
- 词表由本页声明，任何界面不得新增同义名：`是否启用／上下文／不单独设置／自适应／规则结果（default · default）／未应用` 一律退场。`按依据分配` 仍是分配依据（自适应如何分配）的取值名，不是披露列的第五个词；`可用性／说明方式` 只作为层级规则编辑器的规则维名存在，不是本页的列名（列名是 `保存·启用`／`保存·披露`／`本会话·启用`／`本会话·披露`）。
- 结构测试：只允许一个能力面渲染导出；再冒出一个即红。

## 7. 证伪

1. 摘掉运行时或关掉任一全局开关，两列都不变：两列都陈述各自记录写下的字，解析不上屏，所以没有一格跟随当前配置的底层。记录没写的那一维：保存列写 `自动`、本会话列写 `继承`，它们是「这里没有记录」，不是被推导出来的默认。
2. 换入口，只有地址集与写权变：地址集决定整列存不存在，能陈述的行随之增减，而词、值、回执不变。
3. 同一（对象, 地址）在两个入口给出同一值、同一词、同一条记录、同一种回执。
4. 屏幕不出现「未观察／未记录／未证明／未确认／不可用／暂不可用／未启用／未应用」任何变体。
5. 从任意入口都读得懂每一格：遮住同行其他格后，该格的地址仍可判定。

## 8. 显式限制

以下是本契约无法原样兑现、必须以限制形式承认的点。它们不是实现缺口，而是契约自身形状的后果。

**8.1 会话入口不固定保存地址，因此保存两格只陈述。** 会话入口固定的是本会话记录，不是新会话默认；控件只落在这次入口固定的那个地址上，所以 `保存·启用` 与 `保存·披露` 在该入口只有陈述。要改默认必须换入口——设置入口固定新会话默认，且保存的改动到新会话的第一次读取才被读到，它不是「已生效」。若将来要给会话入口写权，须先在本契约里给「从会话里保存」这个动作一个地址与一条回执，而不是让一格兼任两个地址。

**8.1a 服务行的保存格编辑规则，不参与批量。** 服务行陈述的是 `mcpServers.<server>` 这条规则，它的保存格编辑同一份规则文档里的那一条（选 `自动` 即删掉该维，§8.2）。它没有披露控件，披露格写 `各成员自定`：披露由成员各自决定（§8.3）。批量写的是对象条目，所以不写服务行——那一维由它自己那一格写。


**8.1b 成员某一维由谁作答，只由**本会话记录**里服务那一行写了什么决定；成员自己写下的字优先陈述。** 会话入口陈述的是记录，所以为成员作答的是记录里 `mcpServers.<server>` 那一条（不是保存文档里的同名规则——那是解析，见 §8.1c）：它为某一维写下一个不是 `自动` 的字，才为该服务的成员作答，回执点名那一层。记录写 `自动` 是另一件事：那是这一维的**删除**，合并时把那一维从规则里去掉（与保存地址删掉对象规则同一件事，§8.2；`test/capability-environment.test.js` 的「session choices migrate combined preferences independently and reject unknown dimension evidence」用一条物品规则演示同一条折叠——会话 `自动` 让保存的 `关闭` 从合并策略里消失，服务条目走同一条路），所以该维不再由服务作答，成员回到类别／默认那一层——本页不陈述那次回落，成员行仍按「自己没写」写 `继承`；记录**没写**这一维才是 `继承`：它对规则不出声，保存地址的答案原样保留。两个词因此在同一格里并排时不是同义词：`继承` 不出声，`自动` 删掉这一维。成员自己的条目写了这一维时，作答在成员这条地址上：值列与回执都陈述成员写下的字，回执不点名服务——点名会与同一行的值列相反（值列说这一行写了这一维，回执说这一维属于上一层）。代价是本页陈述记录、不陈述规则链的优先级：运行时先取服务那一层（由保存文档与记录合并得到）的答案，所以成员那格写 `启用` 不保证该成员在这个会话里被给到，要知道谁压住谁只能读服务行自己的那一格。控件不受影响：写权只由这次入口固定的地址决定（§1），不由别的层是否作答改变。

**8.1c 保存格只陈述为这个对象写下的那个条目。** 一行一格只回答「这份记录为这个对象写了什么」：`policy.items.<id>`（服务行是 `policy.mcpServers.<server>`）里写下的那一维照写，没写就写 `自动`。分类规则、成员行上的 server 规则与文档底层会在运行时为这个对象作答，但那是解析：它们不是这个（对象, 地址）持有的字，既不上屏、不改值，也不压住控件，因此成员格上不会出现「控件的写权在别的层」这种问题，也不需要第二套控件。写入器另有一条判据：`internal/runtime-config.js` 把 `capabilityPolicyForConfig(...)` 无条件写进 resolved config，两份文档逐字节相同，所以 `capabilityPolicySaved` 记下这份文档是从记录的 `capabilityPolicy` 解析来的还是系统合成的——首次写入因此从记录自己的层起，合成出来的底层永远不进记录。

**8.2 撤销一条对象规则就是保存格写 `自动`。** 保存格陈述的是地址对该对象写下的值；把它选成 `自动` 就是把这一维从对象层删掉（记录为空时连条目一起消失），规则链随即由上一层重新作答——「非法状态不可表示」想要的结果，与「移除对象规则」这个动作是同一件事，不需要第二个入口。写下一个与规则链答案相同的值是另一回事：那一维确实写下了，保存格陈述写下的字而不是 `自动`，代价是记录里多出一条与推导结果同值的规则。

**8.3 服务行的披露格陈述「这个决定在哪」，不是披露取值。** 服务行陈述的是 `mcpServers.<server>` 这条规则，而这条规则**可以**自己写下一个披露字：继承规则窗口编辑它、`set session mcpServers.<server> disclosure <字>` 也接受它、导入的方案可能带着它。写下时它在运行时为**自己没写这一维**的成员作答（规则链的层序是类别 → 服务 → 成员，成员自己的字更高，见 §8.1b），但服务行的两个披露格仍写 `各成员自定`——披露的决定位置在成员那里，服务行不陈述一个「服务自己的披露」。回执不受影响：它陈述这份记录写下的每一个字，包括只有披露字、可用性没写的那种规则（那时回执写 `disclosure <字>`，不写 `未写下`）——否则回执会否认同一次读里已经带着的字。三个代价：成员自己都写了披露时，服务那一层的字没有成员行点名；搜索或筛选把成员行藏起来时，服务规则的字只留在会话入口的回执里（设置入口没有回执列，那一层在那边只在继承规则窗口里可读）；服务行只在它自己写下那一维时才陈述它，没有写下就没有字可陈述。

**8.4 绑定行的两个保存格取自绑定文档，不是能力配置，且采纳记录的「未写下」按条算。** 绑定不是能力：它的保存地址是绑定文档（`enabled` 与 `modelContext.includeDeclaration`），本会话地址是采纳记录（`use` / `skip` / `damaged`）。采纳记录只承载取舍、不承载披露，所以绑定行的 `本会话·启用` 是两态按钮、`本会话·披露` 陈述 `继承`——这一行的两格形状由采纳记录决定，不是缺控件。映射进本页的词表时，`includeDeclaration` 为真读作 `人机·全文·首轮`，为假读作 `仅模型·目录·首轮`。绑定行只在会话入口出现：设置入口固定新会话默认，而绑定采纳没有保存地址。一条读得懂的采纳记录会为每个条目写下取舍：它点名的条目写 `不使用`，未点名的写 `使用`。回执栏的 `未写下` 按条算：记录点名了这条才写「绑定采纳记录 · <字>」，否则写 `未写下`。这处不对称是本契约保留的限制——记录决定了取舍，却没有为未点名的条目逐条留字；要让回执在整行都写记录，先得让采纳记录携带每一条的字。

**8.5 `回执` 列的点名粒度是记录加内容，不是文件路径。** 写入通道是一条命令（`/capabilities set …`），回执是它返回的那一句：哪张记录、哪个维度、什么值。本页不陈述日志文件名或字节偏移——那属于写通道，不属于页面。

**8.6 观察表仍借用本页的词。** 设置页的计划与预算观察表用同一份取值词表陈述冻结方案的选择。§6 要求词表唯一，所以它们必须用同一批词；§5 要求观察面不借用本页的**列、行与分区标题**（取值词表共用是它写明的唯一例外），这条仍然成立——两张要求并不冲突：词表共用，列、行、分区标题不共用。
**8.7 应用方案时不写入「由其余配置合成」的策略。** 方案是配置文档的一份拷贝，`capabilityProfileConfiguration` 会把它补成完整文档，所以一份从「未保存过策略」的记录保存出来的方案里同样带着当时合成的 `capabilityPolicy`。应用方案的那次写入按来源判据处理它：与「用这份配置的其余字段合成的策略」逐字相同的策略不属于任何记录，就不写回记录（§8.1c），并且把记录里原有的策略**移除**（设置服务的 `{op:'unset'}`）——所以应用一份这样的方案之后，保存列继续写 `自动`、管理开关也够不到这些格，无论记录此前有没有策略——除非方案还带着旧版 `capabilityOverrides`：那个字段是写下的记录，不是合成的策略，它随方案写回，保存列按 §8.1c 陈述它写下的字；与合成结果不同的策略是写下的记录，照写。仍未收窄的两处：旧版本保存的方案里那份策略若与今天的合成结果不同，应用它仍会被当成写下的记录；一次失败的激活回滚只对策略用 `unset`，与它同源的两个开关（`capabilityRecoveryEnabled`、`modelPreviewEnabled`）仍按提交值写回；记录确有策略时那条分支由「a rollback keeps a policy the committed record had saved」覆盖，仍未覆盖的是没有 `mutate` 的写入器上那两个开关的写回。
**8.8 三处主张只有部分证据。** 服务行的保存格（`mcpServers.<server>` 那条规则）在 jsdom 用例里只钉住「这一行唯一的保存控件是 `保存·启用` 那一格，它的披露格写 `各成员自定`，它没有勾选」；把选中的值写进同一份文档的 `mcpServers.<server>` 由 `changeCapabilityRule` 的用例覆盖（`test/capability-plan.test.js` 里写 `mcpServers.__proto__` 的那条），页面层没有端到端断言。以设置入口为主体那两个浏览器夹具的目录没有服务行，所以它们那边没有对应断言（别的夹具渲染同一份目录时带着服务行，但不写它的规则）。策略写者「从记录自己的层起笔」这条在逐行保存控件的两个分支（§8.1c）与 `set global <id> <维度> <值>` 那条命令上各有用例钉住，提示设置面板的基线分支没有回归敏感断言。设置入口那次未指名的目录读由后端用例钉住行集、两列 `inherit` 与「不列绑定行」，但页面层只用桩替换了这次读，没有端到端断言。§8.3 的两条写入路径各有用例：继承规则窗口写服务规则的披露字由客户端用例钉住，`set session mcpServers.<server> disclosure <字>` 由后端用例钉住。

**8.9 设置入口只陈述宿主在进程作用域的声明，不是新会话的完整声明面。** 未指名会话的那次读走 `hostSupply({})`，它看到的是宿主在进程作用域注册的对象。preset 在 agent 作用域注册的工具与该作用域解析出的 Skill 层只存在于会话作用域，因此它们不是设置入口的行：这个入口既不能为它们写下对象规则，也不能撤销一条——§8.2 说的「撤销不需要第二个入口」只覆盖这次读陈述得到的对象。保存策略在运行时仍按 id 管辖这些对象，所以这不是「它们没有被配置」，而是「这一页够不到它们的条目」。要让它们成行，得让这个入口读一份被点名会话的作用域（行集会变成那个会话的声明面，而写入的仍是新会话默认），或给规则地址第二处入口；两者都是产品形状的改动，不在本契约内。

**8.10 「不给」在三个模型可见面上同时成立，本页仍留着那一行。** §1 给「给不给」写的后果是「说明、发现、执行三面一致地不体现它」，代价在这里说清。三个面是 `tools:sdk` 声明块（说明）、程序的 `tools.*` 成员（执行）、`capabilities.*` 元数据（发现），它们读同一个判据：本会话记录写下的决定，加上这一步实际交付的定义集——宿主自己就是按每一步的准入渲染声明、并据此构造程序成员，所以「注册表里有、这一步没交付」的对象同样不在三个面上。记录一写下「关闭」，三个面就在同一次读里不再体现它，不等下一次组合：记录是这个会话的决定，组合只是记录的一次读法。属于某个能力的 `tool:<name>` 指引段按同一判据处置：它是对这个能力说的、模型可见的话，能力不在这一步的交付集里就没有成员可供给它指引，所以它随能力一起离开——组合是「一次读法」而不是准入，一份比这一步更宽的旧组合不能把它留下；下一步交付了同一个定义，这一节再出现。两个调用通道（`run_code`、`edit_run_code`）是程序被调用的方式而不是能力，不受这条约束。仍然点名它的东西都不是「模型能调用或发现」的主张：本页那一行（用户重新打开它的唯一入口，也是「关闭」这个决定仍然存在的地方）、会话日志里那条记录、已经投递的历史方案消息（它是历史陈述）。由此有三条限制：(a) 一次决定的变更会让声明文本在方案消息投递之前就改变，方案消息陈述的是它被投递时的那份组合，不追认后来的记录；(b) 页面在会话作用域陈述的是该作用域的声明面（§8.9），不是某一步的准入，所以这一步没交付的对象仍有行——否则用户就再也无法为它写规则。宿主不再持有该会话时没有作用域可读，那一页改陈述它日志里最后一版方案，也就是那一步实际交付的面；行集因此随组合收敛，而不是随注册表；(c) 开关关闭或暂停时这条判据不生效：暂停的能力上下文与关闭的管理开关都委托宿主能力与展示，组合与环境都不成立，记录仍是这个会话的选择但不被应用，重开后再生效（`test/capability-environment.test.js` 的「a switch that is off delegates the Host surface, so a recorded closure is retained but not applied」钉住它）。判据不分层：决定由哪一层写下（保存策略里的一条规则，还是策略世代之前冻结、至今未刷新的方案所带的旧版覆盖记录）不改变它意味着什么。关闭一个共享加载器（`tools.skill`）也会撤回那些把它写成唯一模型路径的发现行：还能由用户调用的 Skill 行留下并改说它仅剩的那条路（不再出现 `await tools.skill(`），既无模型路径也无用户路径的行不再是本会话的能力；资源 server 行同理，一次关闭之后 `capabilities.*` 里不再有任何一行叫模型去调用这个会话关掉的成员（`test/capability-environment.test.js` 的「a closure the legacy layer states withdraws the same Skill invocation path with user entry true」「…user entry false」与「a closure the legacy layer states withdraws the resource operation its contract names」钉住这三条）。这条陈述也不是组合的陈述：组合说的是它被组合时的那条路，而记录在这之后写下时就是会话最新的说法（`change` 只写记录，从不写方案），所以可探索的行说的是「组合交付的」与「决定留下的」的交集。Skill 行在那一步只会丢掉模型路径，不会拿到一份组合没说过的路径；资源 server 行的可用性就是「还剩一个操作可陈述」，它所属的 `mcp:<server>` 指引段与 `mcp-resource-servers` 目录条目跟着同一个答案走（`test/capability-environment.test.js` 的「a loader closed after the composition leaves the Skill row only the path it still has with user entry true」「…user entry false」与「an operation closed after the composition leaves the resource row only the calls it still has」钉住这三条）。

派生的两行（`skills.*`、`mcp.*`）比 `tools.*` 多读一个输入，因为它们的契约本身就是一句「怎么调」的话。一条 `tools.*` 行在声明与执行面上的成员身份由三步决定：组合交付过、记录没关掉、这一步的准入交给了程序；派生行说的是同一个交集的第三条边——**这一步的程序真的拿到了那个共享操作**。组合只被组合一次并复用，一步交付得比组合少并不会让它重组（会话什么都没决定），所以一行可以一边属于仍然「被供给」的能力、一边叫模型去调这一步并不存在的成员：关闭窗口之外还有一个更窄的窗口，它的输入是准入而不是记录。读取方是 `capabilities.*` 的桥：它按程序的成员集请求 `metadata`，`tools.skill` 不在其中时 Skill 行只留用户入口或整行离开，三个资源操作只留这一步交付的那些、一个都没有时整行离开；没有观察过准入的调用方继续读组合，因为「没有观察」不是「观察到更少」。同一交集的第三条边也解释了为什么这一步不会「多出」路径：组合没冻结过的操作从来不是这次组合陈述过的，任何行都不会开始陈述它（`test/capability-environment.test.js` 的「a step that withholds the shared loader leaves the Skill row only the path it has with user entry true」「…user entry false」与「a step that withholds a shared resource operation leaves the resource row only the calls the program has」钉住这三条，`test/plugin-program-bindings.test.js` 的「the explorer states the shared operations the cell program has, not the ones the composition froze」钉住桥真的把这份成员集交给了它）。

**8.11 宿主那张 server 目录也是「这一步能调什么」的陈述。**`mcp-resource-servers` 是宿主唯一一段把能力名字当成参数列出来的文本：它列的名字只能作为 `server` 参数交给三个资源操作，而那三个操作是唯一收这个参数的能力，所以它列谁、列不列，说的都是这一步能调什么。装配侧因此按这一步仍然成行的资源 server 行重写它——三个操作一个都没交付时目录列不出任何 server，段落整段离开（宿主原文里那个 `["…"]` 也随之不再出现），`mcp:<server>` 段随它所属的行一起离开或留下：同一个 server 若还交付了 `mcp__<server>__*` 工具，那段 server 说明仍然成立，因为它描述的是那个 server，不是某一次调用的签名。没组成立方案（管理关闭）时没有行可以归属，目录按准入单独判定：三个操作都不在这一步的交付集里就撤回，有一个就保留原文字节。可及路径是宿主自己的逐步准入：`when` 每步重新求值，作用域限制（`agent.ctx.tools.restrict`）只影响那一个作用域的视图，两者都能让「注册表里有、这一步没交付」在这三个名字上成立（`test/context-host-contract.test.js` 的「the resource server directory states the operations the step delivers, not the composition」用 `when` 和真实装配钉住它，`test/capability-environment.test.js` 的「a step that delivers no resource operation leaves the server directory nothing to name」与「a directory this step cannot use leaves even when no composition states the environment」钉住判据本身）。仍然只跟记录走的是这一段之外的归属问题：`mcp:<server>` 说明在管理关闭的会话里没有行可以归属，行集为空时那句话仍可能是宿主对 server 说的话；收窄它要改的是宿主自己的段落归属，而不是这条判据。`supplied` 仍然只是「本会话还有没有」，准入只作用在投影上，所以统计与面板派生的行不受影响。

**8.12 一次 server 的关闭用的是同一个名字。** 记录为某个 MCP server 写下关闭时，它写的是 server 名（`mcpServers.<server>`），不是那个 server 的任何成员名；所以这条决定要沿同一个名字解析到它拥有的每一行与每一个成员：`mcp__<server>__*` 工具行、派生的 `mcp.<server>` 行、该行依赖的 `mcp:<server>` 说明，以及把这个 server 列成 `server` 参数候选的目录条目。四者读的是同一判据的两种写法——策略层的 `mcp:` 规则与记录层的 server 集合，`capabilityRule` 与 `recordCloses` 各自按成员所属的 server 解析，装配侧不需要为其中某个成员再写一条规则；退化路径（还没组成方案、注册表仍持有这些成员）由同一解析回答，所以一份比会话更宽的注册表视图不会把它们留在声明、成员或可探索行里。仍然点名这个 server 的东西都不是「模型能调用或发现」的主张：本页那一行（重新打开它的入口）、记录本身、关闭之前投递的历史消息，以及关闭之后的方案里那条 `selection: 'closed'` 的行——方案陈述的是这个决定，不是假装它从未存在（`test/capability-environment.test.js` 的「a record that closes a server withdraws its members and its resource directory before the composition catches up」钉住的正是组合还没追上的那个窗口，`test/context-host-contract.test.js` 的「a recorded server closure withdraws the rows, the guidance and the directory the server owns」用真实装配钉住这四者，并留两个非空洞对照：注册表视图在关闭后仍列出那个成员，方案在关闭前把那一行写成 `host`）。
