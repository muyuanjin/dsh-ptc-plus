# PTC Plus 上下文优化实施计划

本文把已确认的产品约束组织成可实施、可验证的方案。目标是让模型在普通任务中更容易用对能力，并降低完成任务的总 token 消耗。当前实现已接入冻结会话方案、编译前能力投影、共享 Skill/MCP 目录、受管工具检索、刷新命令和锁定统计适配器；付费任务收益仍需单独校准；当前一轮的固定任务、盲评、解盲和家族用量审计已完成，但机器预算失败，结果仅是单 replicate 观察。

阅读本文不需要访谈记录。正文直接说明决策、原因、输入、失败后的状态和完成条件；文末的源码与文档索引用于定位实现和核验事实。稳定契约由 [ADR 0038](adr/0038-freeze-session-capability-plans.md) 记录，术语由 [CONTEXT.md](../CONTEXT.md) 拥有。标为“实施建议”的内容是供实现验证的具体起点，不等同于已经确认的公共 API、持久化格式或数值默认值。

## 1. 从当前问题推导优化目标

PTC Plus 的价值是让模型连续计算、复用和修订状态。模型为了获得这种便利而反复阅读很长的能力说明、探索已经提供的工具、修正不准确的调用，或者输出本可留在程序中的大量内容时，计算便利就可能被上下文成本抵消。因此，本次工作的对象是完成任务所需的整个模型交互过程，而不只是某一段提示词。

优化前实现已有 `capabilities.tree/find/inspect`，但 `internal/direct-surface-owner.js` 的 `capabilitySdk()` 当时先保留投影后的完整原生 SDK，再追加发现 API 说明。`internal/sdk-projection.js` 主要适配语言说明并排除程序内的 `edit_run_code`，没有按使用情况分配完整和按需契约。发现入口的存在因而不等于原生能力说明已经按需加载。

发现本身也有成本。当前 `find` 按名称或连续词序列确定性匹配，不是语义检索；`inspect` 的 `budget` 限制条目数量，不限制这些条目的文本或 token 总量。让模型依次列目录、猜搜索词、再取说明，可能增加模型往返；只缩短目录而不改善可发现性，同样可能把成本转移到探索和错误恢复。

历史配对实验提供了问题证据，但没有证明单一成因：修正实验中全部任务已报告 traffic 增加 5.67%，普通任务增加 6.60%，双方均完成的普通配对增加 3.60%。完成率和部分质量指标同时改善。另一个实验队列没有 `find/inspect` 调用，因此不能把额外消耗全部归因于能力发现。记录还存在未结算子请求用量未知及 canary 协议问题，这些数字只能支持“收益尚未成立”，不能作为普遍成本结论或本次优化的预期幅度。

由此得到硬验收目标：在代表性普通任务上，相对关闭 PTC Plus 的原生 PTC，任务质量不下降，任务总 token 消耗降低。总量包含主代理、实际子代理、发现、重试和全部可观测模型请求；缓存输入、未缓存输入和输出分别报告。提示词字节缩短、调用轮数减少、缓存命中率提高和高级能力可用，都只是解释结果的中间指标。

## 2. 先确定管理对象，避免优化越过能力所有权

能力管理针对 DSH 作为 harness 及其其他插件正式提供给模型的任务能力。它改变能力是否进入当前有效集合，以及有效能力的说明如何提供；它不重新定义该能力的参数、结果、权限或执行行为。

| 对象 | 管理内容 | 必须保留的区别 |
| --- | --- | --- |
| 原生、插件及 MCP 工具 | 完整说明、按需发现、有效集合中的成员资格 | 原生工具定义、参数验证和实际分派仍由 DSH 拥有 |
| Skills | 目录说明、发现及正文加载入口的一致可用性 | 完整披露是完整目录说明，正文仍在实际使用时加载 |
| MCP 资源和模板 | 可发现的资源来源、条目或模板及其读取路径 | 共享读取工具、具体资源和开放集合不是同一个身份 |
| 子代理、后台任务、工作流 | 管理其实际提供给模型的能力入口 | 通常已经体现为工具，不额外复制调度或会话协调 |
| JS/TS、Node、REPL、PTC Plus 公共 API、Global User Bindings | 不属于本次能力管理范围 | `code.run`、`repl.state` 和发现基础设施不能因低使用率被隐藏 |
| 仅供人使用的斜杠命令和 UI | 不属于模型任务能力 | 刷新命令属于管理入口，其 UI 回执不自动成为模型消息 |

MCP server instructions、工具 guidance 和 Skill 目录有各自的发布者。仅过滤一份生成的 SDK，不能证明这些其他入口也已经同步。实施必须覆盖实际贡献能力信息的公共入口，不能用一个名义上的工具清单代替整个模型表面。

DSH 继续拥有授权、策略、取消、审批、调度、工具验证和分派。本功能不建立第二套权限系统，不创建按名称重新路由执行的私有 registry，不修改宿主源码或安装包。插件中的能力描述索引只能是 owner 事实的派生读模型；索引条目不能成为新的调用权威。

## 3. 配置独立生效，方案由输入计算

配置由能力管理总开关、统计设置和手动配置组成。它们各自表达用户的意图，不再增加自动、手动、关闭三种互斥模式。所谓“只剩手动”是统计不能参与时自然算出的结果，不是另一个需要同步的状态。

总开关决定是否应用本功能的能力管理。关闭管理时交还宿主原有的能力提供方式，保留独立配置供再次使用；这与关闭整个 PTC Plus 插件不同。管理开关也不能放宽宿主本来施加的限制。

手动配置包含可编辑常用基线和单项选择。单项可以显式指定完整披露、按需披露或关闭；未指定的项才进入基线与有效统计的分配过程。自动统计永远不能关闭能力，也不能覆盖单项显式选择。

统计设置只约束统计部分。设置无效、统计关闭或数据坍缩到无法形成有效依据时，能力方案仍能从手动配置和基线计算出来。不能把损坏或缺失的数据伪装成零使用率，也不能因统计出错撤销用户的手动配置。配置在最早可判断的位置校验，UI 明确显示统计依据为何不可用；有效的手动部分保持可用。

一次方案计算按以下依赖顺序进行：

1. 取得该 agent 当前由宿主实际提供的能力事实，排除不属于管理范围的对象。
2. 若总开关关闭，采用宿主提供方式；否则应用单项显式关闭，得到受管的有效集合。
3. 在有效集合中固定单项显式完整和按需选择。
4. 对其余能力，选择足够的工作区统计；不足时参考足够的用户全局统计；都不可用时使用常用基线。
5. 在说明预算内分配剩余的完整契约，其余保持按需可发现。显式完整造成超预算时报告超量，不截断契约或暗中降级。
6. 生成同一份会话方案的说明、发现和执行投影，并保存每项选择的原因，供用户检查。

例如，用户把能力 A 固定为按需后，即使它在全部样本中都被使用，统计也不能把它改成完整。能力 B 没有单项选择且位于常用基线中，统计不足时按预算进入完整集合；有足够统计后，新会话可依据统计重新分配。统计文件损坏时，A 的显式选择和 B 的基线仍然存在。

所有保存的能力配置都遵守会话生效边界：新会话使用新配置，已有会话只在主动刷新后改变。单项关闭、管理开关和统计设置均不能绕过这条规则。这里不改变 Global User Bindings 等范围外设置已经拥有的生效语义，也不重新解释插件级 kill switch。

## 4. 从抗重复计数到可解释的使用统计

### 4.1 统计衡量什么

原始调用次数衡量执行量，不能稳定衡量常用程度。一个异常循环调用一万次，或一个任务创建几十个子代理，都不应抵消许多独立任务没有使用该能力的事实。因此使用会话家族作为贡献单位：一个主会话及其全部后代代理对同一能力最多贡献一次使用。

对能力 c、统计范围 s，取其最近 N 个合格会话家族组成窗口 W。每个家族只有“实际可用”与“实际使用”的证据，覆盖率为：

```text
coverage(c, s) = 窗口内实际使用 c 的家族数 / 窗口内 c 实际可用的家族数
```

N 按能力和范围解释，不是先取全工作区最后 N 次聊天，再把缺失能力的聊天填成未使用。能力从未提供或已关闭的家族不进入分母；完整和按需都属于可用，按需入口未在目录逐项展示不等于关闭。没有分母时结果是无样本，不是 0%。

假设一个窗口内 A 在 20 个家族实际可用，其中 8 个使用过，覆盖率为 40%。这 8 个中的某一家族继续调用一万次，仍为 40%。另外 30 个没有 A 的家族不影响分母。项目搁置一个月也不自行降低这 20 个样本的权重；只有新的合格家族替换最旧样本。

工作区是主要统计范围。用户全局数据只在工作区证据不足时提供冷启动参考，不能把两个层级重叠的同一家族相加成更多观测。用户应能看见选择实际依据了哪一层、样本数、窗口和回退原因。

工作区身份和家族身份是两条独立关系。子代理可能在不同工作区执行，统计写入进程的当前目录不能代替能力实际可用和被使用的工作区。具体归属规则需要覆盖工作区切换、同一路径的不同表示和跨工作区后代；无论如何归属，同一能力在用户全局范围中仍只接受同一家族一次贡献。

### 4.2 证据必须区分可用、调用、加载与成功

统计以宿主真实身份与执行事实为输入，不从模型自然语言、源码里的工具名称或原始日志文本猜测使用。查询能力描述、列出候选名称和 cold replay 不构成这些候选能力的新使用。统计观察本身不调用模型，也不执行被观察能力。

各类能力的使用证据需要在实现前固定口径。建议以“真实进入能力 owner 的一次调用”为工具使用依据，单独保留完成、失败和取消结果；实际执行后失败仍能表明该能力被需要，不能只统计成功调用。参数校验或权限决定已经阻止分派的请求不能伪装成执行，自动重试和历史事件重读不能产生额外家族权重。

Skill 的目录查询不是正文使用。实施建议以实际正文加载并被接受进入模型上下文作为可观测的调用证据，同时明确这不证明模型随后正确遵循了正文。MCP 资源的目录出现不表示每个资源都被使用；共享列表或读取工具自身的调用、某个来源或资源的访问，应按各自身份记录，不相互冒充。这里的事件判据必须经宿主公共契约验证，再固定为统计格式和测试契约。

家族标识来自真实的主子代理关系。不能根据会话标题、工作区相同或提示词自称子代理来合并。统计家族相同也不意味着代理共享权限、能力集合、工作区绑定或 REPL 状态。

### 4.3 进行中家族与恢复后的修订

尚在运行的家族不能因为暂时没有调用某能力，就被当成已经完成的负样本；主代理 idle 也不能证明全部后代结束。历史评估已经出现主进程退出而子请求未结算的情况。

实施建议将进行中观测与可用于分配的样本分开，在宿主可证明的家族活动结算边界形成样本。会话续接仍沿用同一家族身份：后续真实使用可以修订原样本的使用位，不新增样本，也不因重复恢复重新进入窗口前列。窗口顺序需要一个稳定的资格序号，不能采用统计文件最后写入时间。

上述结算建议必须先通过真实会话续接、子代理取消和进程恢复验证。如果宿主不能提供足够的结束证据，需要先明确可观察的结算边界及其偏差，再让统计参与自动分配；不能为了尽快获得样本，把缺失事实当成未使用。缺失、损坏或无法对账的统计可以失去分配资格，但不应阻止当前合法计算。

统计存储只需保存重建这些判定所需的身份、资格和使用证据、版本及汇总，不复制用户正文、工具参数或结果内容。写入应当幂等，并适应多个会话并发和进程中断。具体保存位置、原子写入方法、保留量与格式代际在实现验证后确定；不能先约定一个无法恢复或无界增长的日志格式。

### 4.4 覆盖率的局限与校准

完整说明更容易被模型看到，按需能力的使用率可能因此较低。覆盖率反映的是给定披露环境中的观察使用，不能直接称为任务的真实潜在需求。分母排除不存在的能力解决不了这种选择偏差。

因此，原始观察应保留当时的披露方式和方案版本，以便评估时解释差异；不能用自动计算出的分数反过来证明自动策略正确。校准应使用冻结的普通任务和检索任务，检查长尾能力能否被找到以及总成本是否下降。无需为了“探索”在活动会话中随机重新分配能力。

待校准参数包括窗口 N、最小样本量、完整披露阈值、说明长度的权重，以及是否需要升降不同阈值来降低新会话之间的抖动。这些数值必须有确定性样本和任务评估的依据，不能把维护者个人环境里的使用频率变成全体用户默认值。

## 5. 披露预算要减少总成本，而不是制造查询链

### 5.1 完整、按需与关闭具有不同含义

完整披露提供 owner 定义的完整调用契约，包括正确调用所必需的类型依赖和约束。它不把程序内能力改成顶层直接工具。Skill 的完整披露只到目录说明，正文始终按实际需要加载。

按需披露意味着说明延后提供，能力仍然属于有效集合。导航可以按用途组织并提供搜索入口，无需把每个长尾名称永久写入提示词。模型应能以一轮查询尽量取得匹配的完整契约，而不是被要求固定执行 `tree → find → inspect` 三次模型交互。

关闭则是从有效环境中移除。说明、搜索命中、Skill 目录、适用的资源来源和 REPL 成员应一致体现缺席，不留下可调用占位再报“禁止调用”。关闭也不是撤销已经发生的外部效果，不删除用户历史消息，不构成 Node 环境的安全隔离。

### 5.2 分开预算，合并计量

需要明确约束四类文本：默认完整契约、能力导航与检索响应、压缩后的说明恢复，以及结果与日志预览。它们生命周期不同，不能用一个条目数量上限代替全部文本预算；在任务评估中又必须合并计入总输入成本。

契约成本应包含其实际投递形式、必要公共类型、指引和包装。共享依赖只在实际去重后扣除，不能按工具数量估算。优先使用当前路由可用的本地计量接口；只能估计时，明确单位和误差边界，provider 的实际 usage 仍是最终成本证据。计量不得为每次普通调用发起付费模型请求。

说明放在哪里同样影响成本。现有契约要求配置、模型路由和原生能力视图不变时，插件系统文本与有序 schema 字节稳定，不能仅因不同会话的统计不同就增加例外。实施建议通过 owner 支持的公共组合移除默认全量 SDK 中被管理的重复说明，保留固定的语言与发现入口，在首个被接受的模型步骤前以有来源的会话目录提供该方案的完整契约；之后的展开、刷新和恢复也走可重建的会话消息。首轮即可直接使用的完整契约不能延迟到第一次调用之后。具体公共组合路径需在阶段一证明，不能一边保留原来的完整 SDK，一边追加新目录后声称已经优化。

预算算法先容纳显式完整项，再对未指定项选择有效统计或基线支持的候选，采用确定性排序与裁决。稳定的相同输入必须得到相同排序和字节。单项完整契约过长时不能截断成貌似完整的 schema；自动选择可以保持按需，单项显式完整则显示超额。预算超额允许用户选择，不代表可以越过模型实际上下文容量。

检索响应同样需要有界。建议优先返回预算内最匹配的完整契约，并明确还有哪些匹配没有展开；一个契约本身放不下时提供可继续获取的入口，不能声称已经交付完整说明。公开接口是否扩展现有 `find/inspect` 或新增组合入口，要兼顾原调用兼容性，但不增加一套平行能力索引。

### 5.3 检索与初始常用集

首轮实现优先采用确定性名称、词项、owner 提供的描述及可维护的关键词索引，验证中文、英文和典型任务表达。当前连续短语匹配是可复用的输入，不是检索质量已经足够的证据。语义增强若需要额外模型请求，必须另有明确授权、预算和用量记录，不能作为隐藏的默认学习成本。

初始常用集是一份真正可编辑的配置，不能只有不可修改的代码常量。建议候选覆盖文件定位与读取、内容检索、必要的执行和修改入口；实际条目必须解析为当前宿主可用的准确身份，不能把这些用途名称当作猜测工具名的分派规则。安装中不存在、被关闭或超出自动说明预算的项，不因位于推荐表就凭空出现。

用户应能从设置中看到推荐来源、实际选择和未选择原因，并修改基线或创建单项显式覆盖。初始常用集不是伪造的使用历史；统计有效且充分后可以影响未指定项的新会话分配，但不会改写用户的显式配置。

## 6. 会话稳定性决定方案的生命周期

### 6.1 方案和实时宿主事实不是同一个对象

会话开始时计算并冻结能力方案，记录配置修订、能力身份与契约修订、完整和按需集合、显式关闭、预算和选择原因。恢复会话时重建同一方案，而不是拿最新统计重新计算。活动会话中的成功调用只更新统计证据，不触发当前方案重排。

升级前已经存在、没有新方案记录的会话也不是新会话。迁移应保留其原有能力提供方式，直到用户主动刷新建立受管方案；不能把缺失字段解释为允许按最新统计重排。合法旧格式、统计损坏和方案记录损坏必须分开识别，方案恢复先寻找可验证的记录与刷新提交。无法证明旧方案时明确报告缺口，不伪造恢复成功，也不把插件历史 metadata 的损坏变成未来合法计算的永久失败；具体收缩和继续执行仍服从现有宿主及 PTC 恢复契约。

稳定方案只能约束本插件自己的选择，不能冻结宿主权限、撤销已发生的 owner 卸载，或保证外部 MCP 服务持续在线。宿主能力真正消失、定义不兼容或策略收缩时，以实际宿主事实为准，并通过已有公共生命周期提供准确诊断和必要的模型通知；不能维持虚假的可调用契约，也不能趁机重新排名所有无关能力。

能力身份应能区分来源与成员，不能只用一个显示名称把两个不同 provider 的工具合并。实施建议把稳定能力身份与契约修订分开：前者用于配置和统计归属，后者用于缓存、说明恢复与兼容性验证。纯描述变更与语义不兼容变更如何继承统计，必须通过有判别力的案例后确定；不能假定同名即同一能力，或每次文案修改都丢失全部统计。

每个 agent 只在自己的宿主 scope 内建立方案。家族统计不授权子代理继承父代理没有授予的能力。新子代理使用哪一份配置修订、父会话刷新是否包含已有子会话，需要明确公共生命周期后固定；实施建议先保持每个已存在会话各自稳定，不把一次“刷新当前会话”扩张成未声明的全家族广播。

### 6.2 主动刷新是一项完整转换

刷新命令为 `/capabilities refresh`。它由用户通过 DSH 公共斜杠命令入口触发，不要求用户发送一条让模型替自己执行的提示。命令操作本身不需要发起付费模型请求，但必须使模型在使用新环境前获得与生效方案一致的通知。

一次刷新应具有以下可观察顺序：

1. 读取当前配置和宿主能力事实，准备完整候选方案及差异，尚不改变当前有效方案。
2. 验证候选的说明、发现和执行投影都可应用；记录用户能理解的变化和预算超额。
3. 在宿主提供的安全生命周期边界应用。已经按旧环境生成或正在执行的 cell 不能中途混用新旧两套成员；等待和取消遵守宿主原有机制，不另建调度器。
4. 使实际运行时、发现目录与模型说明共同指向新方案，并持久化足够的版本和来源证据。
5. 通过公共模型消息或 accepted-step runtime context 投递变更通知。UI 命令回执另行报告实际完成、等待或失败状态。

若宿主只能在下一次接受模型步骤时完成通知，则保留明确的待生效状态，在该边界完成同步；不得仅因 UI 显示成功就假装模型已经知道变化。通知暂时受 suppression 约束时同样如此。具体提交与回滚协议必须证明不存在“新运行时配旧说明”的可观察窗口，不能假定公共 API 天然提供跨组件事务。

准备或验证失败时保留旧方案。提交过程发生故障时，应能从持久化事实判断旧方案还是新方案完整生效；不能留下混合方案、重复通知或未报告的半次刷新。重复命令、取消、会话释放和进程重启都应进入同一转换协议，不重复执行原能力的外部效果。

### 6.3 关闭必须覆盖实际入口

关闭验证至少包含生成 SDK、发现查询、实际 `tools` 成员，以及 Skill 和资源共享加载入口中的成员视图。`tools.restrict()` 目前只约束继承工具，scope 自己注册的工具不受同样的 mask 过滤；`guard()` 的调用后拒绝语义也不满足本设计。因此不能只接一层工具过滤就宣告所有来源已经支持关闭。

刷新前保存的工具别名、捕获工具引用的函数及其他 request-owned 引用，也应加入验证。仅重新生成下一 cell 的 `tools` 对象未必足够。旧引用的处置必须符合已有 lease、binding 和状态连续性契约；若公共入口不足以实现承诺，应明确记录这一覆盖缺口，不用拒绝占位冒充移除，也不擅自清空整个 REPL 来换取通过。

模型历史中曾经出现过的能力说明不可能被假装从未存在。刷新通知需要准确说明当前环境的改变，并通过 owner 支持的替换或撤销关系使旧目录不再冒充当前目录；原始会话日志仍作为历史事实保留。

## 7. 压缩恢复和大结果处理服从同一成本目标

冻结方案不能保证按需展开过的说明永远留在上下文中。压缩后，模型可能仍需使用某个能力，却已看不到完整契约。重新投递所有历史说明会抵消压缩效果，完全不恢复又可能重复探索。

因此在独立预算内，只补回近期实际使用、此前已经展开、契约当前仍有效且当前模型表面已缺失的 API 说明。以真实使用证据确定近期性，以公共 ordered surface 和持久化来源确定是否仍可见；不因 raw log 中还有文本就认为模型仍然知道，也不把尚待投递的内容算成已送达。其余 API 继续按需取得，Skill 正文不自动补回。

说明恢复不改变完整和按需分配，也不证明任何变量仍有正确值。现有 binding 仍要求可重建的 journal ancestry 和精确的模型可见 provenance；本次方案没有授权新增默认 REPL 状态投影，不能通过恢复一段 API 文档保留已经不满足条件的计算状态。

大结果和日志则在进入模型上下文的展示边界做有界预览。优先复用 DSH 的 output retention、spill store 和 spill policy，保留完整展示内容的读取位置、截断事实及必要的读取说明。后续读取省略内容不能重新执行原工具，也不能把 spill 文本当成保留了任意类型与对象身份的 canonical 值。

当前 `maxOutputBytes` 默认 64 MiB，是执行或传输限制，达到限制可能影响 cell 或 worker。它不是模型预览预算，不能通过降低该值制造“更少输出”的假优化。程序接收的 canonical 值、模型展示、UI 展示和执行资源限制需要分别验证。

宿主已安装 spill 组件不等于每种部署都已启用有效预算。初始化时要核对实际公共组合和配置；已有宿主截断与插件预览不能重复包裹通知。spill 保存、内容定价或读取位置创建失败时，沿用宿主的数据保留语义并明确本次未能满足展示预算，不能静默丢失内容或把成功计算改成执行失败。若没有可证明的完整内容取回路径，则不能宣称预览功能已经满足设计。

## 8. 用同一来源连接配置、展示和执行

实施应围绕少量明确责任组织，而不是为工具、Skill 和资源各写一套互不一致的规则。下表给出责任与当前接入点；新冻结环境格式为 `ptc-capability-environment/v2`（保留 v1 历史渲染），方案和统计格式见[组件说明](capability-planning-components.md)。

| 责任 | 输入与输出 | 当前实现接入点及约束 |
| --- | --- | --- |
| 配置和用户管理 | 独立开关、统计参数、基线、单项选择；有效配置与校验原因 | `internal/config-spec.js`、`internal/runtime-config.js`、`src/client-settings-view.js`；区分保存配置和当前会话方案 |
| 能力事实采集 | 公共 owner 的准确身份、schema、scope、说明和修订；派生描述快照 | `internal/capability-environment.js` 及宿主公开 registry；不拥有实际分派 |
| 统计归约 | 真实家族关系、可用与使用证据；有界可重建样本 | `internal/capability-statistics.js` 与 `internal/capability-statistics-store.js`；公共调用与会话事件，cold replay 和重复观察幂等，不改封闭 journal 来夹带无关事实 |
| 方案计算 | 配置、可用集合、有效统计、预算；确定性的会话方案和原因 | `internal/capability-plan.js`；不得在渲染和执行入口分别猜测分配 |
| 说明和发现 | 同一方案、owner 完整契约；SDK、目录、检索结果 | `internal/sdk-projection.js`、`internal/program-bindings.js`；保留参数、结果和必要类型语义 |
| 运行时投影 | 同一方案和实际 request-owned 能力；有效成员 | 现有 direct surface 与执行缝 owner；公共能力成员移除需独立证明 |
| 方案恢复和刷新 | 会话记录、当前方案、候选方案；一致生效和通知 | `internal/capability-environment.js` 及公共 commands、Session、maintenance；使用 accepted-step 与准确来源 |
| 结果预览 | 完成的 canonical 结果与展示内容；有界模型文本及取回位置 | 宿主 retention/spill 公共能力；不混入 canonical 计算与 journal 结算 |

持久化至少需要区分三件事：用户配置表示未来意图；统计表示已经观察到的使用；会话方案表示该会话已经生效的环境。把这三者合成一份会被实时覆写的文件，就无法在配置变化后稳定恢复旧会话。

方案记录和刷新事实应由公共会话持久化面支持，具有可校验的版本与来源。统计可以由其自身证据重建；不能仅凭新统计重新生成历史方案。统计损坏只撤销统计依据，方案损坏则意味着该会话环境没有被证明，两者需要不同诊断，不能共用“清空后按最新配置继续”的默认恢复。

统计归约与索引更新应使用增量事实和有界缓存。相同契约不在每次调用重新解析或重新计量，相同已接受消息不重复投递。统计数字、时间戳和排序过程不能进入稳定系统前缀；相同配置、模型路由和原生能力视图产生字节稳定的插件系统文本及有序 schema。会话方案属于动态会话事实，不是放宽这个前缀条件的第四个输入。

## 9. 按依赖顺序实施，每一步都有可区分的完成条件

### 阶段一：验证公共扩展覆盖并固定输入事实

首先建立小规模、无模型调用的能力组合探针，覆盖继承工具、scope 自有工具、Skill、MCP 工具、资源模板及已有工具引用。对每类记录公共事实来源、说明发布者、执行成员移除入口、恢复来源和缺失接口。读取安装包用于核验契约，不修改包。

这一阶段同时验证原生 SDK 的公共组合路径、真实家族身份、调用结算、会话恢复和命令通知入口。产物是一份可执行的覆盖矩阵，以及统计使用证据、资格顺序和方案修订的具体契约。若某类只能通过私有补丁、第二套分派或调用后拒绝实现关闭，该类不能获得“已支持”结论；公共契约缺口需要回到设计约束处理，不能转成静默降级。

完成条件是：每项已承诺能力类别都有可验证的完整接入路径，或明确的阻塞事实与需要解决的接口；任何未覆盖类别都不进入整体完成声明。这里先降低架构不确定性，再编写 UI 和自动排序。

### 阶段二：完成纯方案计算、手动配置和可恢复会话基线

先实现不依赖统计的手动配置、可编辑常用集、完整与按需预算、关闭集合及选择原因。用确定性输入固定结果，接入新会话和恢复路径，证明保存配置不改变已有方案。

随后接入能力说明、发现和实际执行集合，让单一方案同时决定各投影。这里先证明一项能力在完整、按需、关闭之间的区别，再扩展所有类别，避免统计掩盖投影不一致。

完成条件是：统计完全关闭或无法读取时，手动配置仍完整可用；活动会话、恢复会话和新会话遵守各自配置边界；显式完整的超预算行为可见且不丢契约；范围外能力不被管理。

### 阶段三：接入统计与自动分配

按已固定的事件契约归约家族样本，实现每家族贡献上限、实际可用分母、每能力窗口、工作区优先及全局冷启动。统计与方案之间只传递有效证据，数据不可用时退回手动基线。

使用确定性样本校准算法的性质，再接入新会话方案；不要在这一步引入模型辅助分类或无授权付费检索。用户能够看见使用率、样本量和分配理由，并用单项选择覆盖。

完成条件是：重复调用、增加后代、重放、并发写入和恢复均不能刷高权重；不存在的能力不被刷低；新统计不改活动会话；无样本与零使用率保持可区分。

### 阶段四：完成检索、刷新和说明恢复

将检索调整为有界、尽量一次取得完整契约的交互，保留现有发现 API 的兼容关系。完成用户刷新命令及其准备、生效、通知、取消和故障恢复路径，再接入压缩后的说明恢复。

完成条件是：模型不会面对新运行时配旧目录；UI 成功不能替代模型通知；重复恢复不会重复灌入说明；关闭成员不从其他目录或加载入口重新出现；普通计算状态不因刷新被无依据重置。

### 阶段五：接入大结果预览并完成配置界面

在模型展示边界复用宿主 spill 与 retention，证明可取回、无需重执行且 canonical 值不变。设置界面同时展示保存配置、当前会话方案、待刷新差异、统计回退原因与预算超额，不把这些解释全部塞给模型。

完成条件是：大返回值继续可在程序中计算，模型看到明确预览和有效取回入口；统计配置和手动配置独立；设置页、命令回执与模型通知分别表达自己真实拥有的事实。

### 阶段六：测量完整任务收益并确定默认值

先用确定性测试和无需模型的请求投影检查排除错误，再在单独授权的模型评估中比较普通任务质量和全家族 token。必要时增加“插件启用但本管理功能关闭”的诊断组，用于区分计算插件成本与本次优化贡献；最终验收仍必须对比整个插件关闭的原生 PTC。

固定任务、评分、统计初态、初始常用集和参数后运行，不根据中途结果删除不利任务或调整默认值后混报同一实验。冷启动和有足够历史样本的情况分别测量，训练或校准数据不能冒充未见任务结果。默认开关、预算与阈值在证据充分后确定，不在计划阶段虚构最优数字。

完成条件是：普通任务满足质量与总 token 目标，同时所有能力与生命周期契约成立。若只缩短前缀、提升少数高级任务或减少某种调用而总成本仍更高，本阶段未完成。

以下反例既用于测试选择，也用于后续独立审查。它们不是机械要求每行新增一个测试；应由拥有该关系的最小用例和必要集成证据共同覆盖。

| 需要证明的关系 | 判别场景 | 错误实现应暴露的差异 |
| --- | --- | --- |
| 手动配置独立 | 同一显式按需项分别处于统计关闭、损坏和高覆盖率下 | 任何状态都不能把它改为完整或关闭 |
| 完整与按需不同于关闭 | 同一能力依次完整、按需、关闭 | 按需仍能发现并执行，关闭时各供给入口都没有成员 |
| 家族权重有上限 | 一家族一万次调用并创建多个实际子代理，对照一次调用 | 两者对该能力的统计贡献相同 |
| 分母来自可用证据 | 加入大量没有该能力、关闭能力或仅创建未开始工作的会话 | 不得因此稀释使用率 |
| 无样本不是零 | 新安装能力与长期可用但从未使用的能力 | 冷启动和真实低使用率得到不同依据 |
| 恢复不刷新 | 保存新配置、更新统计后恢复旧会话，或升级前没有方案记录的会话 | 原有提供方式保持；新会话可以不同；缺字段不授权自动重排 |
| 损坏的责任不同 | 合法旧格式、统计损坏、方案提交损坏和普通 journal 损坏 | 不混用回退，不伪造环境或重放效果，不永久阻断未来合法计算 |
| 刷新是一致转换 | 执行中刷新、取消、通知受限、提交途中重启 | 不出现混合环境或虚假成功，也不重复外部效果 |
| 移除覆盖真实入口 | scope 自有工具、Skill 显式加载、MCP 共享读取及保存的工具引用 | 单纯过滤 SDK 或只加 guard 无法冒充通过 |
| 目录有界且可发现 | 数千长尾成员及未在导航列名的真实任务能力 | 不无界列名，仍可检索到正确完整契约 |
| 契约长度被真实计量 | 少量极长 schema、共享类型和显式完整超额 | 条目数预算、截断 schema 或漏算类型均不能通过 |
| 说明恢复有证据 | 正文仍可见、刚被压缩、契约失效和仅查询未使用四种情况 | 只恢复符合条件的说明，不恢复 Skill 正文或改变方案 |
| 展示不改变程序值 | 大对象继续计算、读取 spill 内容、spill 失败 | 程序值不变，读取不重新执行，失败不伪装成成功截断 |
| 稳定前缀 | 相同有效输入，后台统计与计数不断增长 | 插件稳定文本与有序 schema 字节不漂移 |
| 全家族成本 | 主代理已结束而子请求仍在进行或用量缺失 | 不得按零计费、只报根会话或宣称已完整结算 |

现有聚焦入口可从 `test/program-bindings.test.js`、`test/sdk-projection.test.js`、`test/direct-surface-policy.test.js`、`test/plugin-program-bindings.test.js`、`test/runtime-messages.test.js`、`test/runtime-config.test.js`、`test/plugin-settings.test.js` 和 Client 设置行为测试扩展。新增责任需要新增相应测试 owner，并同步 `semantic-obligations.json` 的实现与证据图。

开发期间先用 `npm run test:backend:focus -- --list` 定位后端用例，再按真实 owner 和用例名选择 `test:backend:focus`；Client 使用 `test:client:focus`，布局和原生/回退行为分别使用 `test:client:layout:focus`、`test:client:fallback:focus` 的选定 case。不得用完整 gate 发现失败。针对新证据修复后，只重跑受影响责任。

准备交付或提交证明时才按仓库流程冻结 review plan、开展独立责任审查，并对稳定候选运行一次适用的完整 gate：活动 ledger 有未终结 finding 时用 `npm run verify`，否则用 `npm run check`。聚焦测试不授权提交，已有且仍匹配的完整证明不重复运行。普通开发不运行 coverage；发布新版本时才按发布流程运行。文档、独立审查和验证证明各自拥有不同完成条件。

## 11. 模型评估与上线判据

模型评估需要单独的明确授权，以及 provider、model 和 credential-variable 配置。使用隔离的 DSH home 与工作区，不修改日常 profile 或输出凭据。`test:ab` 先以 `DSH_PTC_AB_CONFIG_ONLY=1` 执行对应配置检查；`test:expensive` 使用 `DSH_PTC_ACCEPTANCE_CONFIG_ONLY=1`。配置检查成功只说明配置就绪，不说明模型行为正确。本计划不授权付费运行。

当前这两个仓库评估 runner 经 `pwsh.exe` 调用 Windows DSH，支持 Windows 工作区及 WSL 挂载的 Windows 工作区，不支持原生 Linux/macOS DSH 运行。后续执行应先验证这个前提，并保持 Windows 与 WSL 的运行环境隔离；若目标是原生 Linux 评估，需要先实现并验证相应 runner 支持，不能把现有命令的配置检查解释为跨平台就绪。

主对照固定同一普通任务、模型路由、宿主能力、工作区起点和评价规则，比较插件关闭与候选插件启用。普通任务为主要验收层；静态 import、跨 cell 状态和复杂值等能力探针单独报告，不能用基线缺少某种高级语法的失败替代普通任务收益。

每次实验至少回答以下问题：

- 任务是否真实完成，最终产物与关键说明是否正确；质量差异是否由盲评和独立 oracle 支持。
- 所有实际家族成员是否纳入；未结算请求、物理重试或缺失 usage 是否仍有未知成本。
- 缓存输入、未缓存输入、输出分别多少；reasoning、缓存写入等 provider 细项按其口径披露，重叠项不重复求和。
- 首次说明、按需探索、错误修复、结果取回和压缩后恢复各贡献了多少成本。
- 在冷启动、统计成熟、长尾能力、短任务和委派任务中，结果是否一致；哪些分层仍有回归。

不能用日志中的逻辑步骤数推断未记录的物理请求数，也不能把未知费用填成零。若无法完整对账，报告必须限制结论，不能用更低的已记录 token 宣称完整任务成本下降。模型结果展示文本也不能替代 canonical 值作为类型或精确结果 oracle。

质量门槛、配对方式、样本量及不确定性报告方式应在付费运行前固定。报告同时保留全部普通任务与双方都完成的次要分层，避免筛掉失败任务后得到漂亮均值；总量与逐任务差异同时展示，防止少数超大任务掩盖普遍回归。只比较费用时还需要明确价格口径，不能把 token、缓存和账单互相替代。

正式启用默认值前，必须同时通过语义与生命周期验证、用户配置可操作性验证、当前官方 DSH 的公共面集成验证和完整任务收益验收。尚未通过时保留显式实验配置和准确限制，不将“功能已经接上”表述为“优化已经完成”。

## 12. 尚需证据收敛的细节

这些问题不重开已经确认的产品原则。它们都有明确的下一步和完成判据；若证据表明必须改变稳定契约，才重新提交该具体冲突。

| 问题 | 当前实施起点 | 收敛证据与未通过后果 |
| --- | --- | --- |
| 各能力类别能否一致移除 | 从公共 owner 视图及作用域集成，首先检查自有工具和共享加载器 | 阶段一逐类探针；缺失接口时保留缺口，不声称全范围完成 |
| 家族何时具有可计分资格 | 进行中观测与可用于分配的样本分开，续接修订同一身份 | 真实结束、续接、取消及子代理未结束案例；无证据不得制造负样本 |
| Skill、失败调用、资源的使用判据 | 使用实际加载或分派证据，结果状态另存 | 验证调用入口与 accepted-step；不以描述查询或语义猜测代替 |
| 身份和契约变化如何继承统计 | 来源身份与契约修订分开 | 同名不同源、仅文案改变、不兼容 schema 三类反例 |
| 工作区与家族如何交叉归属 | 以真实工作区证据计入局部范围，全局仍按家族去重 | 跨工作区后代、工作区切换及路径别名；不能用写入进程目录归属 |
| 子代理采用哪个配置修订 | 每个既有会话稳定，刷新当前会话不隐式广播 | 验证新建和恢复子代理的公共 scope；不得扩张能力或统计权重 |
| 刷新的安全提交与通知 | 候选准备后在宿主允许边界一致生效 | 故障注入、重启、suppression 和旧引用；无完整提交证据不报成功 |
| 参数、初始条目和默认开关 | 配置可编辑，数值和实际能力身份由校准确定 | 确定性样本、检索评估与预先固定的普通任务 A/B |
| 统计造成的披露偏差 | 记录披露方式，使用独立任务评价 | 长尾可发现性和分层总成本；高覆盖分数本身不算收益 |
| 持久化和性能边界 | 三类事实分离、幂等增量归约、有界缓存 | 并发写入、中断恢复、长期窗口滚动及大目录负载 |
