# 能力面板：施工契约（已被取代）

## 0. 权威

**本文的页面形状已被 [能力面：概念契约](capability-surface.md) 取代。** 现行列集、取值、回执、入口与唯一渲染器由那份契约决定；本文继续生效的部分是 §1 的红线、§5 的写通道（行上的决定走的仍是同一条命令）与 §9 的落地位置，以及读路径的一致性要求。下文出现的七列、证据列、设置页清单投影都随该契约失效，保留在这里作为历史来源，不再是缺陷判据。


非目标：不跨会话检索能力；不改冻结语义与 `/capabilities refresh` 的同步含义；不展示 prompt 原文、恢复快照或 worker 内部；不改 REPL 控制台与工作台的分工；**本面板不陈述物化**——方案由运行时在执行前构建，面板只陈述供给、记录与证据；不新增写入器、RPC 写操作或第二写通道。

## 1. 红线：取值不得由面板之外的开关决定

一个字段、一句文案、一个控件状态，若它的取值能被面板之外的任何来源改变——某个进程／服务／运行时／命令没有在运行，或任何全局开关没有启用——它就是缺陷。

判定只有一句：**把那个来源摘掉，这个值会变吗？会变，它就不许存在。**

这条覆盖两类来源，不是一类。「没有在跑」和「没有启用」是同一个错误的两种写法：都让面板去陈述一件它没有资格陈述的事。屏幕上的「未观察／尚未清点／暂不可用／未启用」之所以禁止，是因为它们都是同一个翻译动作的产物：把面板之外的缺失，翻译成面板之内的状态。

推论：面板不需要知道有没有 PTC 运行时，也不需要知道某个开关是开是关；它一旦知道，就一定会在某处把这个知识画到屏幕上。行不存在，是唯一合法的「不能做这件事」的写法。

**这条分界线不落在运行时的有无上，落在「声明面」与「运行时」上。** 两者只差一句：

- **会话的声明面属于会话，必须读。** 这个会话作用域里的工具注册表视图、该作用域解析出的 Skill 层、prompt 装配在该作用域贡献的段，都是宿主对这个会话的供给。会话还有 agent 时，这三样都在它的 scope 上；`agent` 在这里只是取 scope 的句柄，不是「会话可用」的判断，也不是运行时。把它当成运行时来回避，就是把会话自己的声明面误记成 §1 禁止的来源。
- **PTC 运行时不属于声明面，一律不读。** worker、`canRefresh`、`run_code` 是否存在、方案投递（`prepare`／`refresh` 的重建与投递）、`session.append` 回答的是「这个会话现在能不能执行」，面板从不问这个问题。它们一旦被读，§1 的翻译动作就会以另一种拼写回来。
- **会话的 agent 已不在时，作用域随之消失**，面板读这个会话自己记录的冻结方案（§7）。冻结方案是会话的事实，不是运行时状态；拿宿主平面顶替它就是把这个缺陷换了方向——把「这个会话的声明面读不到」画成一张更小的表。记录里本来就没有面时（没有方案、方案损坏、或组合时就没有要求库存）这条读失败并点名缺的那条记录，而不是退回宿主平面、也不是画一张空表。

分界只在读哪一处声明：有没有 agent 决定读 scope 还是读那份记录，不决定任何一格怎么写。

## 2. 概念

| 概念 | 回答的问题 | 边界（属于 / 不属于） | 属于它的后果 | 不得混淆的邻居 |
| --- | --- | --- | --- | --- |
| **供给** | 宿主对这个会话声明存在什么 | 属于：该会话作用域里的工具注册表视图（含 preset 在 agent 作用域注册的工具）、该作用域解析出的 Skill 层、prompt 装配在该作用域贡献的 MCP／资源服务声明；这个会话的 agent 已不在时，属于它自己记录的冻结面。不属于：这个会话选了它没有、它有没有被证明用过 | 一条供给至少一行；供给没有，行就没有 | 记录：供给说「存在」，记录说「选了什么」 |
| **记录** | 这个会话写下过哪些决定 | 属于：绑定取用事件、能力选择事件。不属于：运行时构建出的方案、worker 装了什么 | 没有记录 ⇒ 该格取跟随保存的值；只有最后一条已投递方案带 `sessionOverrides` 的旧会话按那条方案折算出的同一条记录作答；绑定取用记录损坏 ⇒ 该行报记录损坏 | 供给：记录不能说某条目存在 |
| **证据** | 这个会话里有没有一条被接受的执行证明它被拿到过 | 属于：`tool/result` 的 `meta.dshPtcPlusCapabilities.used` 含该 id。不属于：方案、安装、模型是否知道 | 有 ⇒ 一个标记；没有 ⇒ 空格子，不是否定的词 | 记录：记录说「选了」，证据说「拿到过」 |
| **行** | 哪些对象各自构成一个可决定的单位 | 属于：宿主声明的能力、声明的 MCP 服务、全局绑定文档里 `enabled` 的条目。不属于：没有声明的、没有被供给的、统计聚合出来的 | 一行至少一个控件；对象不能被单独决定，它就不是行 | 组与批量：批量是「对已存在的行同时做同一个决定」，不产生行 |
| **控件** | 把一条新记录写进这个会话 | 属于：本会话的决定。不属于：全局配置（在设置页）、运行时动作 | 一行必有，永远可点，没有失败分支；写不进去说明该行不该存在 | 设置页的全局开关：它不决定这一行 |

被删除的概念：清单可用性、就绪、处境、投递、`scope`、`plan`、`management`、`live`、`unreadableSupply`。它们不回答任何别的决定，只把面板之外的缺失翻译成界面。**没有这个概念，就没有它的词。**

## 3. 行

- **能力行**：每个宿主声明的能力一条，恒在。声明没有的条目不会因为配置、记录或运行时有无而出现或消失。
- **服务行**：每个被声明的 MCP 服务一条，`mcpServers.<server>` 是它自己的决定。它是行，不是一批行：整台服务关掉是这个对象自己的决定，不是「筛选后批量」的替代品。
- **绑定行**：全局绑定文档里 `enabled` 的条目一条。未被供给的条目不进本面板——把它画成一行只会得到一个按不动的按钮。
- 行集只由供给决定；配置、记录、证据都不增减行。

现行列集是 `对象 | 类型 | 来源 | 保存·启用 | 保存·披露 | 本会话·启用 | 本会话·披露` 加 `回执`（会话入口），由 [能力面：概念契约](capability-surface.md) §4 决定。下面这段是历史形状，不是缺陷判据：

- **保存**：当前配置里的值。能力行曾两维并写（`自动 · 自动`）——「自动」不是取值，这正是契约把它换掉的原因。
- **可用性／披露**：本会话记录的值，控件就在各自那一格，一格一个控件。
- **证据**：有执行报告时出现标记。这一列已随裁决四移出决定页，换成点名记录的回执列。

## 4. 词表

下面这张表是历史词表，不是缺陷判据：现行列名、取值与回执由 [能力面：概念契约](capability-surface.md) §4 与 §6 决定，本文的 `可用性`／`证据` 列名与 `开启`／`宿主`／`完整`／`按需`／`自适应`／`已证明` 已随该契约退场。

没有否定词。每个词陈述一件存在的事实。

| 列 | 取值 |
| --- | --- |
| 来源 | `DSH 工具`｜`MCP`｜声明的 MCP 服务器名（全部列出，以 `、` 连接）｜`多个服务器`｜Skill 来源桶｜`技能`｜`全局绑定` |
| 保存·可用性 | `开启`｜`关闭`｜`自动` |
| 可用性 | `开启`｜`关闭`｜`自动`｜`继承` |
| 保存·披露 | `宿主`｜`完整`｜`按需`｜`自适应`｜`自动` |
| 披露 | `宿主`｜`完整`｜`按需`｜`自适应`｜`自动`｜`继承` |
| 可用性·取用 | `使用`｜`不使用` |
| 证据 | `已证明` |

`自动` 是「这份记录没有为这个对象写下这一维」，`继承` 是「跟随保存列」，两者不互答。没有记录时可用性列与披露列写 `继承`，不写空、不写「未记录」。日志没有任何选择记录、而最后一条已投递方案带着 `sessionOverrides` 时，这两列陈述的是那条方案折算出的同一条记录（`decided`，标记 `legacy`）；那条方案没有带任何选择时仍是 `继承`。方案的选择表读不出来时这条读是 `unreadable`：能力行没有表达它的词，这两列照常写 `继承`，`记录损坏` 只属于绑定组那条记录（见 §9 的未交付项）。

唯一的例外，且必须同时满足三条：**只由 `classifyBindingAdoption` 返回 `unreadable` 触发**（记录存在但无法解析；记录不存在返回 `none`，不产生这个词）；**陈述的是那条记录，不是面板的状态**；**同一行的控件仍然可点，写一条新记录即取代它**——`记录损坏`。它存在的理由只有一个：另一种做法是替会话报告一个它从未做过的决定。这个词只在面板的行上出现：模型可见的绑定目录没有位置表达「记录不可读」，它对同一条记录发布整份供给，所以 `记录损坏` 不能被读成模型目录的陈述（见 §9 的未交付项）。

一个工具名同时被两个 server 命名空间命名时（`mcp__docs__deep__search` 同时以 `docs`、`docs__deep` 开头），来源列列出这两个 server；历史载荷只声明「有多个 server」而没有名单时写 `多个服务器`。两种写法都陈述存在的事实，来源列不写「未确认／未知／unknown」。

## 5. 写通道

一个意图：把一条新记录写进这个会话。写者只有一个，回执只有一种。

- 绑定 → 取用事件。能力／服务 → 选择事件（携带 id 与选择）。两者同形，都是这个会话的日志事件：`user/message` 携带 PTC 的 `source.form`，不新增事件类型（未知类型会让整份日志拒读）。
- 写者是**这个会话当前的写所有权**，不是「有没有 PTC 运行时」：
  - 会话在 DSH 里活着（`sessions.get(id)` 有它，即使没有 PTC 运行时）：用它的 `session.append`。
  - 会话是冷的（不在 `sessions.get`）：用持久化写句柄 `open(id, 'write')` → `append` → `flush` → **close**，并照运行时交还路径的做法先 `snapshotSessionEvent` 再 `foldSurface` 验证，再 append。
  - 两个分支写的是同一条记录，回执由写者统一给出。**新会话不进入 PTC 模式时，它是活着的会话，走 append**——这正是今天会抛「select an active PTC session」的那一格。
- 命令事务（`/binding`、`/capabilities set`）与面板控件走同一个 owner、写同一条记录、给同一种回执。人类输入与面板不是两条路。
- 记录的物化在运行时：`preStep` 发现记录摘要与现有方案摘要不同时重建方案；`reconcilePendingChoice`、`pendingCommand`／`pendingPrevious` 失去依据，删除。
- **控件没有失败分支。** 没有禁用、没有预检、没有「先启用某开关」。凡是「这一行现在不能改」的情形，都说明该行不该存在。

一个必然的推论：会话记录了选择，这个会话就是被管理的。全局开关决定这份记录**是否被应用**，不改变页面的任何一格：关掉时记录照旧保留、两列照常陈述，新的决定要到重新启用后才改变运行结果（`src/client-capabilities-view.js` 的格子不读这个开关；它决定的是方案的 `enabled`，以及只由管理开关决定的那种配置是否被发布）。要它成为 §1 禁止的那个来源，除非它开始改变某一格的值——那正是这条推论禁止的。

## 6. 面板形状（出稿依据）

一个 Modal（`管理会话能力`），五区，顺序固定：

1. **头**：标题 + 当前会话标识 + 关闭。
2. **工具栏**：搜索、类型筛选、来源筛选、批量（对已勾选的行做同一个决定）。
3. **行区**：表格，§3 的列。
4. **绑定组**：表格下方，同一套行与列语义；组永远在，行可以为零，零行就是空表，不配一句解释。
5. **底部**：最近一次写入的回执。能力写入按当前界面语言陈述这次写了哪条记录、什么选择、写进哪个会话或全局设置；绑定组的写入回执是 `/binding` 命令返回的原文（英文），面板不改写它。回执不陈述证明程度，原始载荷留在命令自己的结果里。

行不可展开：面板不陈述第六件事。七列已经分别陈述供给、记录与证据，行里没有可再展开的陈述。

禁止出现在截图上：侧栏、产品名、版本号、服务状态、整块 `disabled` 的区域、空表头配一句解释的整块区域、任何否定词。

**图与词的分工**：稿决定版式、层级、控件形态与密度；**版式以本节文字为准，稿是它的实现目标**；文字一律按 §4 的词表写，图片模型生成的文字不作为契约。两者冲突时以本节与 §4 为准。

## 7. 读契约

一次读，三个来源，全成功或全失败：

1. **会话头与事件**：同一次日志取用（`sessionLogOf`：`readSessionLog({id}, query)`；宿主没有 projection 服务时取该会话自己的 `snapshotEvents()`）同时给出 header（含工作目录）与事件。会话头与事件来自同一次日志取用；该次取用失败则整次读失败，不返回部分行集——没有 header 就没有目录，日志读不出时目录也没有。事件只用于取记录与证据。
2. **供给**：读这个会话自己的声明面。两条分支，都不碰 PTC 运行时：
   - **会话还有 agent**（任何 DSH agent；不看 `canRefresh`、不看 `run_code`、不看 worker）：`assemble({ agent, scope: agent, ptcPlusCapabilityObservation: true })`、`toolSchemasForAgent(agent)`、`observeSkillsAt({ scope: agent, cwd })`。观察标志让这次公共装配保持被动：它贡献该作用域的段，不准备、不投递，也不重贴 model-facing 传输投影。`agent` 只作作用域句柄——用它判断会话是否可用、调用 `change`／`prepare`／`refresh` 的运行时分支、或 `session.append`，都是缺陷。
   - **没有 agent 的冷会话**：从会话日志里最新一条方案消息的 `source.snapshot.capabilities` 取面（id／category／name／presentation），交给同一条行合成路径。这是这个会话记录的冻结面，不是宿主平面。这条记录能陈述面的前提是它真的冻结过一份库存：一份记录的 `settings` 经 `requiresCapabilityInventory` 判定为不要求库存时（能力与上下文总开关关闭，或能力管理关闭且记录的策略未启用统计与恢复——判据与组合时同一个 owner，`effectiveCapabilitySettings` 先按总开关压掉管理、统计与恢复）`capabilities` 是空数组，它陈述的是「这次组合没有把任何能力供给模型」，不是「宿主没有声明」。没有方案、方案损坏、或这种没有库存的记录，都让这条读失败并点名缺失的那条记录：不拿宿主平面顶替，也不返回空表——宿主平面只回答「宿主声明了什么」，不回答「这个会话被供给过什么」。
   配置：`capabilityConfiguration(currentConfig)`。
3. **绑定文档**：`bindingRows` 读的全局绑定供给（`readUserBindings`），只为绑定组那几行，且只在全局绑定开关打开时读；它读不出时整次读同样失败，不返回部分行集。

来源在实现里各自读，便于定位错误；但**任何一步失败就是整次读失败**：不做部分成功的响应。少了几行而屏幕不说，就是谎。

这条读只有一个入口：`describeSessionCatalog`，两个入口都读它。请求指名会话时读该会话自己的日志与供给（同一个 scope，或同一份冻结方案）；不指名会话时读 `hostSupply({})`，即宿主自己的进程级声明（不含 preset 在 agent 作用域注册的条目），不是任何会话的陈述，因此不充作会话的供给，且这样一次读不列出任何绑定行（绑定采纳没有保存地址）。读路径不得调用 `change`／`prepare`／`refresh` 的运行时分支、不得写（`session.append`）、不得 reconcile 待处理提案，也不得用 `canRefresh`／`run_code`／worker 判断这个会话能不能读：读不产生写，不改变进程态。

读要么给出完整行集，要么整次失败。不存在部分成功的响应：少了几行而屏幕不说，就是谎。失败不是状态，是缺陷——面板给出原始错误、出错的文件或来源，以及重试；空表只表示「宿主真的没有声明」。

响应（`ptc-capability-session-catalog/v2`）：

```
{ schema: 'ptc-capability-session-catalog/v2', sessionId,
  rows: [ { id, kind: 'capability'|'server'|'binding',
            name, category, source,
            saved,        // 每行都有：能力/服务行取自己的规则，绑定行取绑定文档
            session,      // 本会话记录的值；绑定行另带 recorded 标明这条采纳是否被写下
            record,       // 能力/服务行：记录自己的字，layers 标明每一维由哪一层写下
            evidence } ],  // 能力行：boolean
  config: { bindingsEnabled } }
```

- 没有 `live`、没有 `scope`、没有 `plan`、没有 `management`、没有 `unreadableSupply`、没有 `capabilities: null`、没有 `defect` 字段。
- 失败走 RPC 错误通道，带原始错误；错误不分类来源枚举——来源枚举正是运行时重新溜回来的入口。

## 8. 验收

截图必须能判定：

1. 五区齐备且顺序正确；没有 §6 的禁止项。
2. 行区有真实的能力行与工具行（`tools.*`，含 `tools.mcp__<server>__*`）与 Skill 行（`skills.*`），条数可数；有被声明的 MCP 服务行。
3. 每一行都有控件，形态是下拉或按钮，不是开关。
4. 绑定组在表格下方，每行一个取用控件；组存在，即使零行。
5. 全屏文字不含否定词族：`未观察`、`尚未清点`、`不可用`、`暂不可用`、`未记录`、`未证明`、`未启用`、`未确认`、`未知`、`unknown`、`unconfirmed`。
6. 没有整块 `disabled` 区域。
7. 新会话、不进入 PTC 模式打开面板：1–6 全部成立；进入 PTC 模式再打开：行集、行数与控件数不变。
8. 点任一控件都能得到一种回执，底栏文字，与有无运行时无关。

**证伪方式**：把运行时摘掉重开面板，行集改为这个会话记录的冻结面：它与活读的差异只允许是方案冻结之后新注册的条目（集合差 ⊆ 新注册）；该记录没有冻结过面时（没有方案、方案损坏、组合时没有要求库存）读失败并说明缺的是哪条记录，既不给一张更小的表，也不给一张空表。把任一全局开关关掉重开，行集必须只按供给变化（开关关掉的是供给，不是行里的值）。若变而本文没有授权，实现即缺陷。

## 9. 实施落点

本节只陈述已交付的落点；未交付的部分单列在末尾，读到它们不算读到授权。

- `internal/capability-selection.js`：`ptc-capability-selection/v1` 的正文与词表、`CAPABILITY_ENTRY_ID`（条目 id 的唯一词表）、`normalizeCapabilitySelection`；`capabilitySelectionText` 是一份记录的唯一正文字面；`capabilityRuleOfSelection` 是一个整选择与它陈述的维度规则相遇的唯一位置；`classifyCapabilitySelection` 与 `capabilitySelectionOf` 是启用与披露两列和组合入口共用的三态读（`none`／`decided`／`unreadable`）；`capabilitySelectionOf` 在日志没有任何选择记录时把最新一条已投递方案的 `sessionOverrides` 折算成同一形态的 `decided`（带 `legacy` 标记）：整选择词与维度规则写的同一个决定读成同一条记录，`prepare` 因此原地恢复那条方案而不是重建；有记录时以记录为准；该方案没有带任何选择时仍是 `none`（这两列照常写 `继承`），方案的选择表读不出来时是 `unreadable`，方案的 `source.sessionId` 不是本会话时不作为本会话的陈述。
- `internal/capability-environment.js`：`change()` 是唯一写者，按词表判断后写一条语句，不比较方案、不查运行时、不跑预检；`recordSelection` 通过宿主的 `appendPluginRecord` 把这条语句写成 `plugin:ptc-plus/capability-selection` 记录：决定做出的那一刻就落盘，不占 surface、不需要受保护 head、也不等待任何 step，因此新会话开始前的改动在下一次组合里就生效；记录不进入模型可见 surface，`capabilitySelectionOf` 直接读它（`user/message` 形态只作为 0.5.4 及更早会话的历史载体保留，`scripts/repair-session-log.mjs` 会把被旧版本写在 head 之前的语句转成同样的记录）；写入后把这条事件并进本次观察的切面，紧接着的读不会回到被取代的那条；`prepare()` 在记录与已交付组合的 choices 不一致时重建（比较的是两者陈述的决定，不是拼写），重建沿用该组合的 `sourceSettings`（普通刷新仍以冻结来源为准，只有 `refresh` 读当前保存配置）；`describeSessionCatalog` 按 §7 三源读：`sessionCatalogSupply` 决定读哪处声明（`liveAgentFor` 找到 agent 时由 `hostSupply` 以该 agent 为作用域取供给，否则读 `frozenSupply` 重放的冻结面），并在记录没有冻结过面时失败（没有方案、方案损坏、组合时没有要求库存——最后一种由记录自己的 `settings` 经 `requiresCapabilityInventory` 判定，与组合时的判据同一个 owner），`inventory` 接受 `access` 提供的注册表视图与 Skill 观察结果；server 行在 `capabilityRows` 合成且没有自己的披露；`bindingRows` 用 `bindingAdoptionOf` 的三态写绑定行的启用列（取用）。
- `internal/capability-command-receipt.js`：回执只校验它自己那句话需要的形式（无空白、有界长度）。条目 id 的词表由记录 owner 决定，回执不再保留第二个更窄的词表——更窄的那一个会拒掉会话已经写下的记录，于是写成功而回执成文为失败。
- `src/client-capabilities-view.js`：八列行模型、常驻绑定组、行内控件直接走命令通道、底栏与聊天卡片共用 `capabilityReceiptNotice`；`src/client-copy.js` 拥有页面自己的标签、区域标题与唯一一份取值词表（`capabilities.word.*`，两种语言各一份），词表的形状与退场词由 [能力面：概念契约](capability-surface.md) §4/§6 决定，接线与本地化由它自己的结构用例校对；`client.cjs` 是 `src/` 的构建产物，与 `scripts/client-fallback-smoke.mjs` 的断言在同一次改动里一起走。

未交付，不得读成已交付：

- **模型可见的绑定目录没有「记录不可读」的表达。** 不可读的最新取用记录只在面板的行上读作 `记录损坏`；同一条记录交给模型目录时按「没有否决」处理，因此整份供给仍然发布给模型。要让模型也知道这条记录不可读，需要一个新增的模型可见陈述，本文没有授权它，也就没有它的词。
- **能力选择读不可读时面板没有词。** 一条无法解析的能力选择记录（或方案里读不出的选择表）让这条读成为 `unreadable`，而 §4 的例外只授权绑定组写 `记录损坏`：能力行的启用列与披露列没有词陈述它，仍按「没有记录」写 `继承`。要让能力行也陈述这条记录，需要一个本文没有授权的词，因此这里只把它记作未交付。
- **旧形态只覆盖以 `user/message` 投递的方案。** 一条只存在于命令回执提案里的方案由环境的恢复路径读（`recordedPlan`），不由这条陈述读覆盖：它不是会话的陈述，`prepare` 只把记录读到的选择与那条方案的选择逐项比较，相等时原地恢复那条方案，否则按该组合自己的 `sourceSettings` 与记录重算，那条提案自己的会话选择因此不被恢复（`docs/capability-planning-components.md` 记录了这一边界）。
- **冷会话的 Skill 来源桶没有记录。** 冻结方案里的 Skill 能力带 id、name、description 与调用资格，不带 provider／source 桶（它们不进入冻结能力快照），因此冷会话的 Skill 行来源列只写「技能」，不写活读能写出的桶名。要让冻结面也陈述桶，需要一个新增的冻结字段，本文没有授权它。这是两个面唯一按设计不同的列，`test/capability-environment.test.js` 的「the replayed Skill row states every column the live row states except the provider bucket」把这条边界钉成断言：重放行除来源桶外每一列都必须与活读相同。
- **绑定写所有权只有活会话这一条分支。** `internal/user-bindings-owner.js` 的 `recordAdoption` 要求活的 `session.append`；§5 的冷会话持久化写分支没有实现，冷会话写不了取用记录。
