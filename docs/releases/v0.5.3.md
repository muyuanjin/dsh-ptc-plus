<h3 id="cn-v053">宿主适配</h3>

* 目标发行仍是当前官方 DSH，插件继续使用它的公共扩展面（设置卡片座位、会话投影、能力探测与公共 `Menu`），本版本不要求宿主侧改动
* 旧版本写下的会话日志照常恢复：本版本之前的结算记录没有新的自证字段，恢复按旧规则读取它们，不需要清空会话或配置

<h3>新增</h3>

* 绑定取用变成会话自己的决定：`/binding status` 列出全局提供的条目，`/binding use <id>` 与 `/binding skip <id>` 决定这个会话用不用，`/binding reset` 回到缺省。没有表态就是全部取用，所以升级后不设置也没有行为变化；决定记在会话里，重启后从日志重建
* 全局删掉的条目不能在会话里被"救回来"：它已不在目录里，取用只可能收窄，不存在覆盖复活这条路径
* 设置里新增开关「编辑改写目标单元格」（`editRewritesHistory`，默认关闭）。打开后，已接受的 `edit_run_code` 修订取代目标单元格：后续单元格读到修订的值，目标单元格仍留在日志里但不再参与环境重建，修订不再声明的名字以"被取代"报告（`PTC-R007`），而不是当作丢失
* 能力设置的收据与本面板的面板把三件事分开说：已保存（全局设置记录了这项选择）、已投递（模型可见目录里已出现该项）、已可用（本会话有完成的执行真的取到了它）。保存或发布都不构成"已可用"，没有证据时如实说未证明

<h3>修复</h3>

* 被事后改动的历史记录不再能充当证据：每个结算在发布时留下自己陈述的摘要，恢复折叠会重算并比较它。status、completion 或诊断措辞被改过的单元格会被判为不可信、被跳过并点名（`PTC-R002`），而不是重放一个从未发生过的单元格；判定是终态，不会进入重试
* 改写历史打开时，被取代单元格的绑定以专门诊断点名，而不是静默消失
* REPL 绑定面板说明清单来自哪个运行期：同一运行期内的投影刷新仍然保留清单；上一个进程留下的快照显示为不可确认，并给出原因，不再静默续用

<h3>升级</h3>

* 需要 Node.js `^22.19.0 || >=24.0.0`；升级插件后请重启 DSH
* 不需要配置迁移：新开关默认关闭，其它字段沿用既有配置；旧会话日志不需要清理或重写

```sh
dsh plugin --profile <profile> add dsh-ptc-plus@0.5.3
```

<h3 id="en-v053">Host Compatibility</h3>

* This release targets the current official DSH release and keeps using its public extension surfaces (the settings card seat, the session projection, capability probing and the public `Menu`); no host-side change is required
* Session logs written by earlier versions keep recovering: settlements recorded before this version carry none of the new self-proof fields, and recovery reads them by the older rules, so no session or configuration has to be cleared

<h3>New Features</h3>

* Binding adoption is now the session's own decision: `/binding status` lists the globally supplied entries, `/binding use <id>` and `/binding skip <id>` decide whether this session uses one, and `/binding reset` returns to the default. Saying nothing means every entry is used, so upgrading without touching it changes nothing; the decision lives in the session and is rebuilt from the log after a restart
* An entry deleted globally cannot be revived from a session: it is no longer in the catalog, adoption can only narrow what is supplied, and there is no override that brings it back
* New setting **Rewrite the edited cell** (`editRewritesHistory`, off by default). When it is on, an accepted `edit_run_code` revision supersedes its target: later cells read the revision's value, the target keeps its place in the log but no longer rebuilds the environment, and names the revision no longer declares are reported as superseded (`PTC-R007`) instead of being treated as lost
* A capability receipt and the capability pane now state three facts separately: saved (the global setting records the choice), delivered (the model-visible catalog lists it) and usable (a completed execution in this session actually reached it). Neither saving nor publishing proves usability, and without evidence the pane says so

<h3>Fixes</h3>

* A historical record edited after the fact can no longer serve as evidence: every settlement records a digest of what it published, and the fold recomputes and compares it. A cell whose status, completion or diagnostic wording changed is treated as untrusted, skipped and named (`PTC-R002`) instead of replaying a cell that never ran; the decision is terminal and never becomes a retry
* With history rewriting on, the bindings of a superseded cell are named by their own diagnostic instead of disappearing silently
* The REPL binding panel states which runtime its inventory came from: a projection refresh inside the same runtime keeps the inventory, while a snapshot left by a previous process reads as unconfirmed with its reason instead of being reused silently

<h3>Upgrade</h3>

* Requires Node.js `^22.19.0 || >=24.0.0`; restart DSH after upgrading the plugin
* No configuration migration is needed: the new switch is off by default and other fields keep their values; existing session logs need no cleanup or rewrite

```sh
dsh plugin --profile <profile> add dsh-ptc-plus@0.5.3
```
