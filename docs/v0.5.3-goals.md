# v0.5.3 目标：可证明的状态

## 0.5.2 留下了什么

0.5.2 解决的是**状态连续**：视图变化不再重建内核，绑定不会因为一次重渲染而丢失，编辑是追加而不是改写历史。它把"REPL 环境活着的时候算数"这件事做扎实了。

但它留下一个未回答的问题：**插件对模型说的那些话，凭什么算数？**"这个绑定可用""这条记录没被改过""这个能力已经生效"——这些都只是**声明**，不是**证明**。0.5.2 里已经能看到三种破口：

- 恢复提示说某个名字 live，下一格却 `not defined`（`PTC-R002` 收口了一部分）；
- 保存了全局绑定开关，面板只能说"已保存"，说不出"已投递""已可用"；
- 历史记录被事后改动，插件从记录本身看不出来，因为记录与它的副本永远自洽。

所以 0.5.3 的主题不是再加功能，而是**把声明变成证明**：

> **0.5.3：可证明的状态。** 插件对模型陈述的每一条事实，都要有它能产出、模型能检验的证据；并且永远区分"已配置""已投递""已证明"。

## 概念基元

四个词贯穿本版全部目标，先定义再谈功能。

| 概念 | 回答的问题 | 谁拥有 |
| --- | --- | --- |
| **供给 supply** | 产品声明存在哪些能力、绑定、能力开关 | 全局配置与目录 |
| **取用 adoption** | 这个会话的环境选择用其中哪些 | 会话 |
| **物化 materialization** | worker 真的把它装进环境了吗 | 运行时与 worker |
| **证明 proof** | 有什么可被模型检验的证据 | 日志、探测、诊断 |

三条不变式：

- **I1 层次不可互相代答。** 供给不能代取用，取用不能代物化，物化不能代证明。
- **I2 只有证明可以宣称"可用"。** 没有证明时如实说"不可确认"，而不是默认可用。
- **I3 可证明的事实必须能从会话日志重建。** 重建不出来的，要显式标注为不可重建，而不是假装它不存在。

0.5.2 的教训正好对应 I1：全局开关是供给，会话要不要用是取用，装了没有是物化——三层混成一个"开关"，就会出现"我改了全局，为什么这个会话不变"和"配置关了但绑定还在"这类说不清的状态。

## 目标

### G1 绑定：从"开关"到"环境成员"

**概念纠正。** 绑定不是配置项，是**环境成员**。全局决定目录供给，会话决定取用，worker 决定可用。

- 全局关闭一个条目 = 它不在目录里，会话无从取用。**"覆盖复活已删除条目"这个概念上不存在**，不需要额外的冲突规则去禁止。
- 会话取用是二态（用 / 不用）加一个缺省（未表态即全取），不需要三态哨兵，也不借用能力侧的 `automatic`——那个词的含义是"由宿主推导"，绑定没有可推导的决策。
- 取用 ≠ 物化成功：装失败的名字必须点名（接 `PTC-R002`），曾经 live 后消失的必须点名（`PTC-R006`）。

**验收**：不设会话取用时行为与 0.5.2 完全一致；A 会话不用某绑定、B 会话仍可用；全局关闭后会话不可取用且无"复活"路径；重启后取用关系随日志重建；物化失败在模型可见处点出名字。

### G2 能力与上下文：把"已保存"升级为"已投递"

**概念。** 保存设置只改变供给，不证明模型看得到、也不证明 worker 初始化过。面板与提示必须分开说这三件事。

**验收**：保存后能报告目录是否出现该能力、新单元格能否真的取到它；三种状态（已保存 / 已投递 / 已可用）在面板与模型可见提示中区分；任一层失败都指名，而不是笼统"已生效"。

### G3 历史证据：记录必须能自证未被改动

**概念。** 一份可以被事后编辑、且编辑后仍与自身副本一致的记录，不是证据。执行时要写入**不可重算的快照**，折叠时用它比对。

现有的半成品：`completion` 与诊断已经互相校验（0.5.2），但 `diagnostics` 被改后再重算 `completion` 就自洽了——因为事件里没有第三份独立副本（`message.content` 为空）。

**契约**：快照字段随 journal schema 一起版本化；不一致即判该格不可信；**否决必须是重放终态**，不能进入重试循环（上一次实现因此挂死）。

**验收**：篡改 completion 或 diagnostic 都使该格不可信；恢复矩阵不退化；journal 迁移对旧记录保持兼容。

### G4 改写历史：`editRewritesHistory`

**概念纠正。** "改写历史"不是删除，而是**取代关系**。旧单元格仍然留在日志里，只是不再参与环境构建；它声明的名字以"被取代"报告，而不是以"丢失"报告。

这比"追加"更诚实：不假装旧执行没发生过，而是显式声明谁取代了谁（`supersededBy`）。默认关闭，开启时改写才真正替换目标单元格。

**验收**：关闭时全部既有用例不变；开启时"改写 → 后续格子读到新值"成立；被取代单元格的绑定以专门诊断点名；折叠能从日志重建取代关系。

### G5 快照归属：REPL 面板的 generation

**概念。** 面板显示的不是"当前状态"，而是**某个运行期的一次观察**。需要分开两件事：

- **新鲜度**：同一运行期内的投影刷新——清单仍然有效，不该闪成"不可确认"；
- **归属**：跨运行期的快照——属于上一个进程，必须判为不可确认（既有契约，`repl-memory-projection` 的用例钉着它）。

0.5.2 的客户端兜底只解决了新鲜度，没有表达归属。0.5.3 要在数据里表达"这份清单来自哪个运行期"，而不是靠随机 UUID 与对象身份比较去猜。

**验收**：两个会话并行、其中一个结束时，另一个面板不闪；真正重建后显示不可确认并说明原因；既有契约用例保持绿。

### G6 覆盖率：证据，不是仪式

**概念。** 覆盖率是"这段代码被执行过"的证据；阈值是策略，不是证据。0.5.2 为发版引入了"按改动文件 100% + 历史欠账白名单"，那是策略例外。

**验收**：全局 `lines 100 / functions 100`，白名单清空；`review:finalize` 记录对应证明；发布流程不再需要"按改动文件"的特殊分支。

## 非目标

- 不新增 PTC 语言特性，不改 DSH 的公共契约；
- 不做跨会话共享 worker 或跨会话共享 REPL 状态；
- 不为通过门槛而放宽断言或增加 coverage ignore（除非证明不可达并写入提交信息）。

## 发布判据

1. 六个目标各自的验收项全部有可执行证据；
2. `npm run check`、`npm run coverage`（全局 100%）、`semantic:check`（unknown 0）全绿；
3. `docs/` 中受影响的 owner 文档与 ADR 同步更新；
4. Release 工作流 `stage` 成功，npm 进入 staged 状态；
5. 发布说明按 [release-notes.md](release-notes.md) 的用户视角重写，不以功能清单代替变化说明。
